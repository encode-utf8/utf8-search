# 02 技术方案与开发计划

> 项目：utf8-search
> 目标：为 LLM 提供**免费、高速**的联网搜索服务，效果对标 Tavily，速度对标 DeepSeek 联网搜索
> 说明：方案已按用户确认落地实现，M1/M2/M3 主体完成并通过实测验收；实测数据见 `docs/01` 第 5 节与 `checklist.md` 第 6 节。

## 1. 设计目标与非目标

### 目标

| 编号 | 目标 | 度量 |
| --- | --- | --- |
| G1 | 零付费依赖即可跑通 | 不配置任何商业 Key，搜索 / 抓取 / 重排全链路可用 |
| G2 | 高速 | basic 模式 P50 ≤ 1.5 s；advanced 模式 P50 ≤ 4 s |
| G3 | 结果可用 | 每次返回 3–10 条带标题、URL、摘要、相关度的结构化结果 |
| G4 | 双协议接入 | MCP（stdio / Streamable HTTP）+ REST |
| G5 | 可自托管 | 一条 `docker compose up` 起 SearXNG + 服务 |
| G6 | 接口兼容 Tavily 习惯 | 工具名与参数尽量对齐 Tavily，便于替换现有产品 |

### 非目标（本期不做）

- 不做爬虫全站抓取、建索引、大模型训练数据管道。
- 不自带 LLM 生成答案（答案摘要为可选扩展，默认由调用方模型完成）。
- 不绕过付费墙、登录墙，不抓取非公开数据。

## 4. MCP 工具设计

### 4.1 web_search（核心）

| 参数 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `query` | string | 必填 | 查询词 |
| `max_results` | int | 5 | 返回条数（1-20） |
| `search_depth` | basic / advanced / deep | basic | advanced 抓取约 6 页；deep 抓取约 24 页（对标「读几十个网页」） |
| `topic` | general / news | general | news 会启用新闻源与时间过滤 |
| `time_range` | day / week / month / year | 无 | 时间范围过滤 |
| `include_domains` / `exclude_domains` | string[] | 无 | 站点白名单 / 黑名单 |
| `include_raw_content` | bool | false | 是否返回抽取后的正文全文 |
| `engines` | string[] | 无 | 指定搜索引擎（调试用） |

返回：`query`、`took_ms`、`cached`、`results[]`，每条含 `title`、`url`、`snippet`、`content?`、`score`、`engine`、`published_date?`。

### 4.2 web_fetch（内容抽取）

| 参数 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `urls` | string[] | 必填 | 待抓取 URL（最多 10 条） |
| `format` | markdown / text | markdown | 输出格式 |
| `max_chars` | int | 20000 | 单页字符上限，控制上下文成本 |

### 4.3 search_answer（可选，默认关闭）

对「搜索 + 抓取」结果做摘要。默认不实现，因为生成摘要需要 LLM（会引入成本）。若需要，可选两条路：调用方自己的模型 API，或本地小模型（如 ONNX 量化的中文小模型）。

### 4.4 设计要点

- 不返回裸 HTML，保证 LLM 拿到的都是可直接消费的文本。
- 支持 MCP progress 通知：advanced 模式先返回搜索结果，再补正文，避免客户端长时间无响应。
- 工具描述写清「何时调用、结果如何使用」，提升模型调用准确率。

## 5. 速度优化策略（G2 的关键）

| 编号 | 策略 | 预期收益 |
| --- | --- | --- |
| S1 | SearXNG 常驻 + 定时轻量预热 | 消除冷启动，3.1 s → 1.1 s |
| S2 | 多引擎由 SearXNG 内部并发聚合，服务侧不串行调用 | 搜索结果一次到位 |
| S3 | httpx.AsyncClient 连接池 + HTTP/2 + Keep-Alive 复用 | 省 TLS 握手 |
| S4 | 抓取硬超时 2.5–3.5 s + 凑够 N 条就提前返回 | 消除 28.6 s 长尾 |
| S5 | 三级缓存（查询结果 / 页面正文 / 最终结果包） | 命中 ≤ 50 ms |
| S6 | 抽取限长、跳过非 HTML、跳过超大响应 | 控制 CPU 与内存 |
| S7 | 重排用 BM25 本地实现，不做向量推理 | 毫秒级 |
| S8 | 信号量并发上限 + 按域限速 | 保护上游、降低被封风险 |
| S9 | advanced 模式分阶段返回（先列表、后正文） | 感知延迟下降 |
| S10 | 抽取放到线程池并行执行 | 省 0.3–1 s |
| S11 | 解析线程池规模压到 8（trafilatura 受 GIL 限制，线程越多越慢） | 实测 32 线程单页解析 11 s → 8 线程恢复正常 |
| S12 | 搜索结果已带标题时跳过 `extract_metadata` | 省掉一次等价成本的完整解析 |

## 6. 缓存设计

| 层级 | 存储 | TTL | 说明 |
| --- | --- | --- | --- |
| 查询结果 | 内存 LRU（256 条）+ SQLite | 10 分钟 | key = 归一化查询 + 参数指纹 |
| 页面正文 | SQLite（WAL） | 6 小时 | key = URL，含抽取正文与原始长度 |
| 最终结果包 | 内存 LRU | 5 分钟 | 命中直接返回并标记 cached=true |
| 失败缓存 | 内存 | 1 分钟 | 避免对刚失败的引擎/域名反复重试 |

## 11. 风险与对策

| 风险 | 概率 | 影响 | 对策 |
| --- | --- | --- | --- |
| 上游引擎反爬 / 封 IP | 高 | 搜索质量下降 | 多引擎冗余、健康评分、自动剔除、限速、可配置代理、缓存兜底 |
| 抓取长尾超时 | 高 | 延迟不可控 | 硬超时 + 提前返回 + 并发上限（已实测验证必要性） |
| 正文抽取失败（JS 站） | 中 | 内容缺失 | 跳过并标注；可选 Playwright；Jina Reader 兜底 |
| SearXNG 容器异常 | 中 | 服务不可用 | 健康检查 + 重试 + 直连 Bing 兜底 Provider |
| 合规 / ToS | 中 | 法律与封禁风险 | 只用公开页面、遵守 robots.txt、限速、不做数据转售 |
| 网络环境变化 | 中 | 引擎可达性改变 | 部署到可自由出网的机器；支持国内源适配开关 |
| MCP 规范演进 | 低 | 兼容性 | 采用 mcp SDK v2（支持 2026-07-28 规范），传输层可切换 |
| SSRF（抓取调用方 URL） | 中 | 内网探测 / 数据泄露 | 抓取前协议与地址校验，拒绝内网与保留网段，逐跳复检重定向 |

### SSRF 防护（M4-4.1 已实现）

/extract、/v1/extract、MCP web_fetch 与 advanced/deep 抓取都会访问调用方给出的 URL，公网部署后可被用来探测内网服务（如 http://127.0.0.1:6379）或云元数据（http://169.254.169.254/latest/meta-data/）。

- 入口统一走 src/utf8_search/security.py::check_url：仅放行 http/https，拒绝内网 / 回环 / 链路本地 / 组播 / 测试网段等保留地址，以及 .internal / .local 等内网域名与单标签主机名。
- 域名会解析后逐个校验全部 IP；解析失败则放行（连接阶段同样会失败，不构成 SSRF，也避免无 DNS 环境误伤）。
- 重定向由 PageExtractor._download 手动逐跳跟随，**每一跳都重新校验**，防止 302 跳到内网绕过检查；超过 MAX_REDIRECTS 放弃。
- 开关与上限：UTF8SEARCH_BLOCK_PRIVATE_HOSTS（默认 true）、UTF8SEARCH_MAX_REDIRECTS（默认 5）。内网自用抓内网 wiki 时显式关闭开关。
- 已知限制：不做 DNS 固定，理论上存在 DNS rebinding 时间差窗口（记录为已知限制）。
