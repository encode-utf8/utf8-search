# 05 服务器部署手册（公网 Linux / 无自有域名）

> 项目：utf8-search
> 编写日期：2026-09-25
> 适用场景：一台公网 Linux 服务器，**没有自有域名**，用 `sslip.io` 免费 DNS 名拿受信任证书
> 本次实际部署：阿里云新加坡 `43.106.104.49`（Ubuntu 22.04.5 / x86_64 / Docker 29.8.1 / Compose v5.5.1）
> 证书状态：**已签发 Let's Encrypt 真证书**（`43.106.104.49.sslip.io`，2026-09-25 16:19 GMT 签发，2026-12-24 16:19 GMT 到期）

## 1. 架构与端口

```
                公网                ┌──────────── 服务器 ─────────────┐
  客户端 ──── 80/443 ──────────────▶│  Caddy（TLS 终止 + 反代）        │
                                    │        │ 容器网络               │
                                    │        ▼                        │
                                    │  utf8-search:8000（应用）        │
                                    │        │                        │
                                    │        ▼                        │
                                    │  searxng:8080（搜索聚合）        │
                                    └─────────────────────────────────┘
```

| 服务 | 容器名 | 端口映射 | 对公网 |
| --- | --- | --- | --- |
| Caddy（反代） | `utf8-search-caddy` | `0.0.0.0:80`、`0.0.0.0:443`（tcp+udp） | ✅ 唯一入口 |
| 应用 | `utf8-search-app` | `127.0.0.1:8000:8000` | ❌ 仅回环 |
| SearXNG | `utf8-search-searxng` | `127.0.0.1:8888:8080` | ❌ 仅回环 |

设计要点：**应用与 SearXNG 都只绑回环**，公网只能经 Caddy 的 443 进入。这样即使云安全组误放行了 8000，宿主机也不会接受非回环连接（内核实测：从 `172.30.19.109:8000` 直连返回 `Connection refused`）。

云安全组入方向已放行 **22 / 80 / 443**（2026-09-25 完成）。其中 80 不是业务端口，而是 HTTP→HTTPS 跳转（实测 308）
与**证书续期校验**（HTTP-01）的通道，详见第 5.3 节。

## 2. 前置条件

### 2.1 系统依赖

```bash
# 最小系统依赖：python3-venv 用于本地跑验收脚本；Docker 需已就绪
apt-get update -qq
apt-get install -y python3.10-venv
docker --version && docker compose version
```

> 新装 Ubuntu 常缺 `python3.10-venv`，不装会导致 `python3 -m venv` 报 `ensurepip is not available`。

### 2.2 阿里云安全组（**必须手工在控制台改，无 API 权限改不了**）

**当前状态：已放行 22/80/443（2026-09-25 由用户在阿里云控制台完成）。**
注意这**不是一次性动作**：证书每 3 个月自动续期时同样走 80/443，长期关掉会让证书在到期后静默失效（见 5.3）。

入方向只放行三条，其余全部拒绝：

| 协议 | 端口 | 来源 | 用途 |
| --- | --- | --- | --- |
| TCP | 22 | 你的固定 IP（建议） | SSH |
| TCP | 80 | `0.0.0.0/0` | HTTP→HTTPS 跳转 + Let's Encrypt HTTP-01 校验 |
| TCP | 443 | `0.0.0.0/0` | HTTPS 唯一业务入口 |

**不要放行 8000 / 8888。** 应用与 SearXNG 只绑回环，放行也无用，还会误导后续排障。

安全组没放行 80/443 的直接后果：

- 外部客户端连不上（`curl` 超时，不是 404/502）；
- Let's Encrypt 无法回连做校验，证书申请失败：
  `urn:ietf:params:acme:error:connection ... Timeout during connect (likely firewall problem)`。

以上两条在 2026-09-25 放行前都实测复现过；放行后变成 `80 → 308`、`443 → 200`，ACME 签发成功。

自检办法（在本机执行，本机 ufw 默认 inactive、iptables INPUT ACCEPT 时即可判定是安全组问题）：

```bash
ufw status                                  # 期望 inactive
iptables -S INPUT | head                    # 期望 -P INPUT ACCEPT 且无 DROP 规则
curl -sS https://api.ipify.org; echo        # 确认公网出口 IP
```

### 2.3 免费域名（无自有域名方案）

`sslip.io` 会把主机名里内嵌的 IP 解析回该 IP，因此不用买域名也能走标准 ACME：

```bash
getent hosts 43.106.104.49.sslip.io     # 期望输出 43.106.104.49
```

> ⚠️ **隐私提示**：任何公开受信任证书都会被写入**证书透明度（CT）日志**，这是全网可查、永久的公开记录。
> 用 `43.106.104.49.sslip.io` 意味着**这个 IP 与主机名会被公开索引**（可用 crt.sh 之类的服务搜到）。
> 单纯自签不产生 CT 记录。若不希望 IP 进入 CT 日志，就不要申请公开受信任证书。

## 3. 首次部署

```bash
cd /root/utf8-search

# 1) 虚拟环境与依赖（仅本地验收脚本需要；服务本身跑在容器里）
python3 -m venv .venv
.venv/bin/python -m pip install -U pip
.venv/bin/python -m pip install -e ".[dev]"

# 2) 配置
cp .env.example .env
#    改这三项（见第 4 节）：
#      UTF8SEARCH_SEARXNG_URL=http://127.0.0.1:8888
#      SEARXNG_SETTINGS_FILE=./searxng/settings.yml
#      UTF8SEARCH_MCP_ALLOWED_HOSTS=43.106.104.49:*,43.106.104.49.sslip.io
#      UTF8SEARCH_API_KEYS=<自己生成的随机 Key>

# 3) 整栈拉起（SearXNG + 应用 + Caddy）
docker compose up -d --build

# 4) 看状态：三个服务都应在跑，后两个应为 healthy
docker compose ps
```

首查注意：SearXNG 冷启动后**第一次查询要 20–60 秒**加载引擎，别刚起来就下结论。

## 4. 环境变量清单

### 4.1 本次部署实际生效的关键项

| 变量 | 值 | 说明 |
| --- | --- | --- |
| `UTF8SEARCH_SEARXNG_URL` | `http://127.0.0.1:8888` | 宿主直连 SearXNG（本地验收用）；容器内由 compose 覆盖成 `http://searxng:8080` |

| `UTF8SEARCH_API_KEYS` | 随机 Key（见 `.env`） | 留空 = 关闭鉴权，公网禁止留空 |
| `UTF8SEARCH_RATE_LIMIT_RPM` | `60` | 每个 Key 每分钟请求数上限 |
| `UTF8SEARCH_DOMAIN` | `43.106.104.49.sslip.io` | Caddy 站点域名（compose 传给容器） |
| `UTF8SEARCH_BLOCK_PRIVATE_HOSTS` | `true`（默认） | SSRF 防护，公网部署必须保持 true |

### 4.2 不要动的项

| 变量 | 原因 |
| --- | --- |
| `SEARXNG_SETTINGS_FILE=./searxng/settings.local.yml` | 那是**本机走本地代理**用的版本。云上直连外网，用它会让引擎全部不可达。 |
| `UTF8SEARCH_HTTP_PROXY` | 云上无本地代理，保持空。 |

### 4.3 关于 `UTF8SEARCH_MCP_ALLOWED_HOSTS`

实现见 `src/utf8_search/server/http_api.py::_transport_security`：MCP 的 DNS 重绑定防护按 Host **精确匹配**，支持 `host:*` 通配，并且总会自动追加 `127.0.0.1:*` / `localhost:*` / `[::1]:*`（保证本机调试不被挡）。

配置时要按客户端**实际发出的 Host** 来写：

| 客户端访问方式 | 实际 Host | 是否需要写进白名单 |
| --- | --- | --- |
| `https://43.106.104.49.sslip.io/mcp` | `43.106.104.49.sslip.io` | ✅ 已写 |
| `https://43.106.104.49/mcp`（裸 IP） | `43.106.104.49` | ✅ 由 `43.106.104.49:*` 覆盖 |
| `http://127.0.0.1:8000/mcp`（服务器本地） | `127.0.0.1:8000` | 自动追加，无需配置 |

### 4.4 上游并发闸门调参（M5）

四个参数控制「同时打到 SearXNG 的聚合请求数」：

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `UTF8SEARCH_UPSTREAM_MAX_CONCURRENCY` | 3 | 同时打到上游的请求上限（0 = 关闭闸门，不推荐） |
| `UTF8SEARCH_UPSTREAM_QUEUE_LIMIT` | 12 | 最多允许多少请求排队（队列满立即 429） |
| `UTF8SEARCH_UPSTREAM_MAX_WAIT` | 4.0 | 主源排队等待上限（秒），超时立即 429 |
| `UTF8SEARCH_UPSTREAM_OPTIONAL_WAIT` | 1.0 | **兜底型**调用（news 的通用引擎补充、Bing 兜底）取容量的有限等待（秒） |

**服务契约（按并发分层，替代原先的“general@30 成功率 ≥25%”单点阈值）**

| 并发 | 成功率 | 降级率 | 空结果率 | P95 | 定位 |
| --- | --- | --- | --- | --- | --- |
| **@≤5** | **100%** | 0% | 0% | **≤5.2s** | 设计运行区间（正常部署应把并发控制在这里） |
| **@10** | **≥95%** | 0% | 0% | **≤6.5s** | 可承受的突发 |
| **@30** | 仅作**容量陈述**，不设阈值 | 0% | 0% | 记录值 **3.0-8.5s**（不设阈值） | 超容量点：超出部分用**秒级 429** 快速返回 |

> 实测补充（2026-09-27/28，真实上游）：@≤5 与 @10 两档**逐点达标**；**@30 的 P95 只能算“多数样本满足”**
> —— general 实测 3.0-6.9s、news 3.7-8.5s（超容量点的尾延迟由上游抖动主导，@30 的成功率也只有 15-27%）。
> 把 @30 当容量陈述而不是 SLA 来读。

**要不要把上限调大（例如 6）？**（详见 `docs/reports/m5-concurrency-gate-20260927.md`）

- 上游**健康**的日子（能稳定跑 ~4 req/s）默认 `3` 会多付约 **20-30% 的尾延迟/墙钟**：
  并发 10 实测 P50 2.4-2.6s → 3.2-3.4s、墙钟 13.4-13.8s → 16.5-17.6s。若你的上游长期稳定、
  更在意延迟，可以把上限调到 **6**。
- **风险**：上限一旦超过上游真实容量，就回到「全体一起慢」——实测并发 30 打爆上游时单请求会飙到
  **10-12s**（连接异常 + 本地重试各 5.5s）。调大后请用 `scripts/loadtest.py` 复测，并盯
  `/metrics` 的 `utf8search_upstream_requests_total{result="error"}`：**> 0 就说明已经打爆**。
- **news 的补充路只在主源不足时才触发**（判据：主源凑不满 `max_results`），所以多数 news 请求只打 **1 路**上游；
  需要补时是**串行两跳**。`UTF8SEARCH_UPSTREAM_OPTIONAL_WAIT`（默认 1.0s）是这条**兜底路**取容量的等待上限 ——
  拿不到容量就直接 429，**绝不静默跳过**（跳过会把中文长尾的空结果交给用户，是质量事故）。
  重扫 1.0 / 1.5 / 3.0s：news@10 降级率 0%、空结果率 0%、P95 5.96 / 6.43 / 6.10s → 取最小 1.0s。
- **news@30 的“净负”是好日 artifact**：交错复测（base→gate→base→gate，各 2 轮）显示——**健康日**基线能 100% 服务、
  只是尾延迟 6.5-9.6s，而闸门把 80-85% 的请求变成 429（成功率 15-20%）、把服务到的请求 P95 压到 4.9-6.6s。
  也就是说**好日子里 news@30 用闸门得不偿失**（没有坏日要防）。
  **坏日**（上游被打爆、`docs/04` §4.4 记录的单请求 19s 级）闸门才是保护：它把“全体一起慢”换成“多数快速失败 + 少数可控”。
- **news 高并发的扩容方向**（而不是调闸门参数）：
  1. **多实例 SearXNG + 前置负载均衡**：闸门上限是**单进程、单上游**的，加实例才能提高总容量（`limit` 可按实例数分摊）；
  2. **只在确认上游余量时提高 `MAX_CONCURRENCY`**：判据是 `/metrics` 里
     `utf8search_upstream_requests_total{result="error"}` 长期为 0 且上游 P95 稳定；一旦出现 error 或
     单请求回到 10-12s，说明已经超过真实容量，必须调回；
  3. **news 为主时**优先保证 `OPTIONAL_WAIT`（兜底路）而不是主源并发——news 的召回依赖那一路，
     牺牲它换来的是空结果而不是速度。
- 指标：`GET /metrics`（沿用 REST 鉴权，需带 Key）暴露 `upstream_active` / `waiting` /
  `rejected_total{reason}` / 排队与上游延迟直方图，排障时先看 `rejected_total` 的 reason 构成。

## 5. 证书：申请、续期与自签兜底

### 5.1 当前状态：已签发真证书

- 域名：`43.106.104.49.sslip.io`（`sslip.io` 免费通配 DNS，把 IP 写进主机名即可解析回本机）
- 签发机构：Let's Encrypt（公开受信任 CA，客户端**零配置信任**，不需要安装任何根证书）
- 有效期：`2026-09-25 16:19:35 GMT` → `2026-12-24 16:19:34 GMT`

```
subject=CN = 43.106.104.49.sslip.io
issuer=C = US, O = Let's Encrypt, CN = YE1
notBefore=Sep 25 16:19:35 2026 GMT   notAfter=Dec 24 16:19:34 2026 GMT
```

> ⚠️ **CT 日志提醒**：公开受信任证书会把**域名与 IP** 写进证书透明度（CT）日志 —— 全网可查、永久公开
> （可用 crt.sh 之类的服务搜到）。本项目接受这一代价，换取客户端零配置信任；若不想让 IP 进 CT 日志，
> 就只能退回自签，代价是每个客户端都要装根证书。

### 5.2 双签发者：真证书优先 + 自签兜底

Caddyfile 里配置了**双签发者**，先试 Let's Encrypt，失败立刻退回内置 CA 自签：

```caddyfile
tls {
    issuer acme       # 真证书：客户端零配置信任
    issuer internal   # 兜底：ACME 失败时立刻给一张自签，绝不退回明文 HTTP
}
```

任何时刻对外都只有 TLS，不会因为证书问题裸奔 HTTP（API Key 明文过公网是硬性禁止项）。
当前真证书已签发，自签兜底**未在使用**，只作为「万一 ACME 暂时失败也不中断服务」的保险。

### 5.3 首次签发的操作（已执行，留档）

1. 安全组放行 80 与 443（见 2.2）；
2. 域名解析到本机（`getent hosts` 验证）；
3. 之后强制重新申请。**注意：只 `restart` 不够** —— Caddy 会直接复用存储里那张尚未过期的自签证书，
   必须先把自签证书删掉：

```bash
# 删掉已缓存的自签证书（Caddy 存储路径实测为 certificates/local/<域名>/）
docker compose exec -T caddy sh -c "rm -rf /data/caddy/certificates/local/43.106.104.49.sslip.io"
docker compose restart caddy
docker compose logs caddy --since 5m | grep -iE "obtaining certificate|challenge failed|certificate obtained"
# 期望：certificate obtained successfully ... issuer ... acme-v02.api.letsencrypt.org-directory
```

> 该流程先在安全组未放行时预演过：删证书 + 重启后 Caddy 确实重新走了一遍 ACME
> （`http-01` / `tls-alpn-01` 均因超时失败），随后回退到自签、服务全程 200 不中断。
> 2026-09-25 安全组放行后照此执行即签发成功，拿到受信任真证书（见 5.1）。

### 5.4 续期（依赖 80/443 长期放行，否则 3 个月后静默失效）

Caddy 全自动：到期前 30 天开始续，证书与 ACME 账号存放在命名卷 `utf8-search_caddy_data`。

**关键：续期和首次签发走的是同一条路 —— Let's Encrypt 必须能从公网回连本机 80（HTTP-01）或
443（TLS-ALPN-01）。因此安全组 22/80/443 必须长期放行，不能只在首次部署时临时开一下。**

后果很隐蔽，务必记住：

- 若在证书到期前把 80/443 关掉，续期会在后台反复失败，**Caddy 不会主动告警**；
- 旧证书一过 2026-12-24，所有客户端都会看到「证书已过期」而直接拒绝连接，服务等于中断；
- 本证书建议在 **2026-11-24 前后**主动核对一次续期是否成功（Caddy 提前 30 天就该续好）。

核对方式：

```bash
# 证书到期日应从 2026-12-24 变成新的日期；issuer 仍是 Let's Encrypt
echo | openssl s_client -connect 43.106.104.49.sslip.io:443 \
  -servername 43.106.104.49.sslip.io 2>/dev/null | openssl x509 -noout -dates -issuer
# 续期日志（成功会打 "certificate obtained"）
docker compose logs caddy --since 24h | grep -iE "certificate obtained|renew|error"
```

**不要**删这两个卷，否则每次重启都会重新签发，容易撞 Let's Encrypt 配额：

```bash
docker volume ls | grep caddy      # utf8-search_caddy_data / utf8-search_caddy_config
```

### 5.5 自签兜底时的客户端信任方式（当前未使用，留作应急）

自签证书由 Caddy 内置 CA 签发，客户端需信任该根证书。根证书在容器内：
`/data/caddy/pki/authorities/local/root.crt`。

```bash
# 导出到宿主机（data/ 被 gitignore，不会进仓库）
docker compose exec -T caddy cat /data/caddy/pki/authorities/local/root.crt > data/caddy-local-root.crt

# 方式 A：装进系统信任库（推荐，curl / 浏览器 / Python(truststore) 都生效）
cp data/caddy-local-root.crt /usr/local/share/ca-certificates/utf8-search-caddy-local.crt
update-ca-certificates

# 方式 B：只在单条命令里信任
curl --cacert data/caddy-local-root.crt https://43.106.104.49.sslip.io/health

# 方式 C：只信任一次、不校验（仅排障，不要用在真实客户端）
curl -k https://43.106.104.49.sslip.io/health
```

注意两点：

- **Python `httpx` 分两种行为**：`httpx.AsyncClient(trust_env=False)`（本项目自检脚本用的就是这种）
  只认 `certifi` 的 CA 包、不认系统信任库；
  而 MCP SDK 的 HTTP 客户端走 `truststore`，只认**系统**信任库。两者都要覆盖才跑得通 ——
  这也是当初优先把 ACME 修好（换成真证书）的原因；上面的应急流程只在前者失效时用。
- 自签证书有效期很短（Caddy 内部 CA 默认 12 小时）并由 Caddy 自动轮换，客户端信任的是**根证书**（10 年）。

### 5.6 应急：退回自签后如何换回真证书

无需改配置（`issuer acme` 排在第一），只要**先删掉缓存的自签证书**再重启：

```bash
docker compose exec -T caddy sh -c "rm -rf /data/caddy/certificates/local/43.106.104.49.sslip.io"
docker compose restart caddy
docker compose logs caddy --since 2m | grep -i "certificate obtained"
# 期望出现 issuer 为 acme-v02.api.letsencrypt.org-directory 的那条
```

## 6. 验收

### 6.1 测试与脚本执行环境

**凡访问 `127.0.0.1`、需要出网、需要写 `.git`、或需要访问 docker socket 的命令，都必须在
「沙箱外」（直接宿主 shell / SSH 会话）执行**；放进受限沙箱会**静默挂起或直接失败**，
而且往往报不出真正原因。

| 命令类型 | 为什么必须沙箱外 | 典型命令 |
| --- | --- | --- |
| 访问 `127.0.0.1`（本机回环） | 沙箱里的回环是**另一个网络命名空间**，连不到宿主上的 app / searxng | `curl http://127.0.0.1:8000/health`、`:8888`，`scripts/mcp_selfcheck.py --mode all`（会自起临时实例） |
| 需要出网 | 受限沙箱默认禁网 | `pytest -m net`、`git pull`、`docker compose pull`、Caddy 走 ACME 申请证书 |
| 需要写 `.git` | `.git` 常被只读挂载，写操作直接失败 | `git commit` / `git push` / `git worktree` |
| 需要访问 docker socket | `/var/run/docker.sock` 通常不在沙箱内 | `docker compose ...`、`docker exec ...`、`docker restart ...` |

判定口诀：命令里只要出现 `127.0.0.1` / `localhost`、`pip install`、`git` 写操作或
`docker`，先确认自己在沙箱外再执行。

## 8. 常见故障排查

### 8.1 查询返回 0 条 = 引擎不可达（最常见）

按下面的顺序逐层排除，**不要直接改代码**：

```bash
# 第 0 层：服务自己怎么说
curl -sS http://127.0.0.1:8000/health | python3 -m json.tool
#   看 status / searxng / engines.cooling / engines.active

# 第 1 层：容器在不在
docker compose ps

# 第 2 层：SearXNG 直连有没有结果
curl -sS "http://127.0.0.1:8888/search?q=test&format=json" | head -c 300

# 第 3 层：单引擎隔离，看 unresponsive_engines 的原因
curl -sS "http://127.0.0.1:8888/search?q=AI+news&format=json&engines=google%20news" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); print(len(d['results']), d.get('unresponsive_engines'))"

# 第 4 层：服务器本身能不能出网
curl -sS -o /dev/null -w "%{http_code} %{time_total}s\n" https://www.google.com
curl -sS -o /dev/null -w "%{http_code} %{time_total}s\n" https://duckduckgo.com
curl -sS -o /dev/null -w "%{http_code} %{time_total}s\n" https://www.bing.com
```

排查结论对照表：

| 现象 | 判定 | 处理 |
| --- | --- | --- |
| `/health` 的 `searxng=unreachable` | 服务/依赖问题 | `docker compose ps` 看 searxng 是否 healthy；`docker compose logs searxng` |
| SearXNG 直连 0 条、`unresponsive_engines` 全是 `Timeout`/`ConnectTimeout` | 出网/引擎不可达 | 跑第 4 层；若三站都不通，是服务器出网问题（安全组出方向 / DNS / NAT） |
| SearXNG 直连 0 条、`unresponsive_engines` 是 `Suspended: CAPTCHA` / `access denied` | **多为 SearXNG 处罚盒自锁，不一定是 IP 被封** | 先 `docker compose restart searxng` 清空处罚盒，等 40 秒再隔离测一次；可用引擎集合见 `/health` 的 `engines.active` |
| SearXNG 直连正常、应用 0 条 | 服务问题 | 看应用日志；确认 `UTF8SEARCH_DEFAULT_ENGINES` / `NEWS_ENGINES` 配置 |
| `/health` 返回 403 或 JSON 被拒 | SearXNG `settings.yml` 未开 `formats: [html, json]` | 检查挂载了哪份 settings（见 4.2） |

**关于引擎处罚盒（重要，4.2 部署实测踩过）**：SearXNG 内部对失败引擎有"暂停"机制。一旦某引擎（典型是 `google` / `google news`）
被判为机器人，SearXNG 会在处罚期内**直接返回 `Suspended: CAPTCHA`，根本不向上游发请求**。此时 `/health` 会给出
`class=captcha`、`reason=暂停服务: 验证码`、`consecutive_failures` 与 `retry_after`。

所以「连续多轮 100% 失败」几乎都是**SearXNG 自己的处罚盒还没到期**，**不要据此判定「这台机器的 IP 被 Google 封了」**。
4.2 部署当天的证据链：同机同 IP，`google news` 连续 6/6 失败（`Suspended: CAPTCHA`），但
`docker compose restart searxng` 清空处罚盒后立刻 6/6 成功；同机直连 `https://www.google.com/search?q=test` 也稳定 200、无风控页。

**排障动作固定为两步，顺序不能反**：

```bash
docker compose restart searxng     # 第 1 步：清空 SearXNG 处罚盒
# 等 40 秒引擎加载
curl -sS "http://127.0.0.1:8888/search?q=AI+news&format=json&engines=google%20news" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); print(len(d['results']), d.get('unresponsive_engines'))"
# 第 2 步：隔离测（只看 unresponsive_engines 的真实原因，别被处罚盒误导）
```

### 8.2 外部连不上（curl 超时）

| 检查 | 期望 |
| --- | --- |
| `ss -ltn \| grep :443` | 有 `0.0.0.0:443` 监听 |
| `docker compose ps` | caddy 在跑 |
| `ufw status` | `inactive` |
| 云安全组 | 入方向已放行 80/443 |
| 第三方探测 | 从外部请求 `https://<域名>/health` 能通 |

若本机监听正常、本机防火墙放行、但外部仍超时 —— **就是云安全组**，去控制台改。

### 8.3 `/mcp` 一律 421

- 没配 `UTF8SEARCH_MCP_ALLOWED_HOSTS`（或没重启应用让配置生效）；
- 白名单里的 Host 与客户端实际发的不一致（注意端口：`host` 与 `host:port` 是两个不同模式，用 `host:*` 覆盖带端口的形态）。

### 8.4 所有请求 401

- 客户端没带 Key，或带的位置不对（支持 `Authorization: Bearer`、`X-API-Key`、body `api_key`）；
- 改了 `.env` 但没 `docker compose up -d utf8-search` 让配置重新注入；
- Key 里带了引号/空格（`.env` 里不要加引号）。

### 8.5 大量 429

按 Key 限流（`UTF8SEARCH_RATE_LIMIT_RPM`）。确认客户端没有并发重试风暴；需要更高配额就调大该值并重启应用容器。

## 9. 附：安全组放行前的本地等价验收

当安全组还没放行时，外部客户端连不上，但仍可以验证「Caddy TLS → 应用」这一整条链路是否正确。做法是让本机把
域名解析到回环地址，等价于"公网已可达"（**仅用于验收，验完必须还原**）：

```bash

cp /etc/hosts /tmp/hosts.bak
printf '\n127.0.0.1 43.106.104.49.sslip.io\n' >> /etc/hosts

# 2) 让本机 Python 信任自签 CA（注意 httpx 只认 certifi、MCP SDK 只认系统库，两处都要）
cp data/caddy-local-root.crt /usr/local/share/ca-certificates/utf8-search-caddy-local.crt
update-ca-certificates
cat data/caddy-local-root.crt >> .venv/lib/python3.10/site-packages/certifi/cacert.pem

# 3) 等价验收（Host / SNI 都与公网一致）
curl -sS https://43.106.104.49.sslip.io/health
K=$(grep -E '^UTF8SEARCH_API_KEYS=' .env | cut -d= -f2-)
.venv/bin/python -u scripts/mcp_selfcheck.py --base-url https://43.106.104.49.sslip.io --api-key "$K"

# 4) 还原（务必执行，否则本机会一直把域名指向自己）
sed -i '/43\.106\.104\.49\.sslip\.io/d' /etc/hosts
cp /tmp/cacert.pem.bak .venv/lib/python3.10/site-packages/certifi/cacert.pem   # 若之前备份过
getent hosts 43.106.104.49.sslip.io   # 应重新解析到公网 IP
```

注意：它验证不了「公网可达」和「Let's Encrypt 回连」，那两件事只能靠安全组放行 + 真实外部访问。

### 14.5 备份与恢复

```bash
BACKUP_SKIP_CACHE=1 bash scripts/backup.sh /root/deploy-backups-<日期>   # 跳过可重建的 SQLite 缓存
bash scripts/backup.sh                                                  # 全量（含 cache.db ~12MB）
```

* **默认加密**：`backup.sh` 产出 `utf8-search-backup-<日期>.tar.gz.enc`（AES-256-CBC + pbkdf2 200k 迭代），
  `SHA256SUMS` 记的是**密文**的校验和；**口令只从环境变量/口令文件读，缺口令直接拒绝执行**
  （要明文必须显式 `--allow-plaintext`，不推荐）。口令来源二选一：
  ```bash
  export BACKUP_PASSPHRASE='<强口令>'                    # 交互场景
  BACKUP_PASSPHRASE_FILE=/root/.utf8-search-backup.pass  # cron 场景：600 权限文件（当前服务器已配置）
  ```
  ⚠️ **口令保管**：口令文件**不进备份、不写日志**，必须与备份**分开保存**（异机密钥库 / 密码管理器）；
  口令丢失 = 备份不可恢复（没有后门路径）。
* **必须备份**：`.env`（**机密**：API Key / Host 白名单）、`docker-compose.yml`、`Caddyfile`、
  `searxng/settings.yml` + `settings.local.yml`、`data/`（缓存 + 测量产物 + 长稳 CSV/JSON + 巡检日志）。
* 打包产物：`…tar.gz.enc`（600）+ `SHA256SUMS`，目录权限 700；异地上传前可再叠一层加密（age/gpg）。
* **解密恢复步骤**：
  ```bash
  cd <备份目录>
  sha256sum -c SHA256SUMS                      # 先验密文完整性
  openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -pass env:BACKUP_PASSPHRASE \
      -in utf8-search-backup-<日期>.tar.gz.enc -out restore.tar.gz
  gzip -t restore.tar.gz && tar -xzf restore.tar.gz -C /tmp/restore   # 解到临时目录，不要覆盖现网
  cd /tmp/restore/utf8-search && docker compose config >/dev/null       # 解析校验
  ```
* 恢复演练（**不要在现网直接演练**）：解包到 `/tmp` → `sha256sum -c SHA256SUMS` → `docker compose config` 解析 → 比对 `.env` 键集合。
  实测结果见 `docs/reports/m6-ops-hardening-20260930.md`（明文版）与 `docs/reports/20260930-p3-backup-encryption.md`（加密版）。

### 14.6 常见运维动作

| 现象 | 处理 |
| --- | --- |
| 引擎长期 `Suspended: CAPTCHA`（google/google news 最常见） | **`docker compose restart searxng`**：本地处罚盒立刻清空（实测重启后秒级恢复 12 条结果）。不要改配置等它"自然恢复" |
| 改了 `.env` 但行为没变 | 用 `up -d --no-deps` **recreate**（restart 不会重新注入 env）；确认 `docker inspect` 里的 `Config.Env` |
| 复测时效/相关性门槛数字异常好或异常差 | **必须绕缓存**：`CACHE_QUERY_TTL=600`；同查询直接打会读到旧快照（实测同刻 28% vs 56%）。脚本加唯一后缀或等 TTL |
| 磁盘增长 | 观察点：`data/cache.db`(SQLite，可重建)、`data/soak-*.csv`、`data/ops-check*.log`、容器日志（已轮转 30MB/容器）。清理优先删 cache 与旧长稳 CSV |
| 上游整体变慢（坏日） | 闸门会把过载请求快速 429（`Retry-After`），**不要靠调大 `max_wait` 硬扛**；这是上游容量问题（docs/04 §8 有结论） |

### 14.7 ⚠️ 不要启用多 worker

上游并发闸门（`upstream_max_concurrency=3`）是**进程内**计数器。若用 `uvicorn --workers N` 或多容器横向扩，
**每个 worker 各自持有 limit**，全局并发 = N × limit，等于把"保护上游"的设计废掉；
真要多 worker，必须先按 worker 数**分摊** limit（例如 3 个 worker 时每个设 1），或把闸门改成共享存储（Redis）版本。

### 14.8 备份保留策略的排除名单与"永不删光"（2026-10-01 加固）

* **`BACKUP_EXCLUDE`**（空格分隔）列出**永不参与清理**的目录名/glob。默认 `deploy-backups-20260929`
  —— 那台服务器上的这个目录装的是**人工回滚资产**（`.env` 备份、compose 快照、历史镜像/容器 JSON、压测与自检证据），
  不是 `backup.sh` 的自动产物；保留策略必须跳过它（P8 修正版会 `rm -rf` 整目录，代价不可接受）。
  例：`BACKUP_EXCLUDE="deploy-backups-20260929 deploy-backups-manual-*"`。
* **永不删光保险**：每次清理前先算出**最新一份产物**（按 mtime），它本身、它的 `SHA256SUMS`、它所在目录
  **一定不会被删**（即使全部超期）。日志里会打印 `（保险）最新产物不会被删：<路径>`。
* **清理范围**仍是 `BACKUP_ROOT`（默认 `/root`）下的 `deploy-backups-*`，按 mtime；依旧**先打印清单再删**。
* ⚠️ **cron 跟随当前签出的分支**：`cron` 执行的是 `/root/utf8-search/scripts/backup.sh`，
  所以**脚本内容取决于仓库当时 checkout 的分支**。实测 2026-10-01 03:30 的自动备份产出的是**明文包**
  （当时工作区不在本分支上）。**在把本分支合并进 `main` 之前，cron 行为不可依赖**；
  已把当天明文包重加密并销毁明文（见 `docs/reports/20261001-backup-retention-hardening.md`）。
