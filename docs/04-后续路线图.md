## 4. M4 详细任务（P0，建议先做）

### 4.1 SSRF 防护（✅ 已完成，2026-09-24）

**问题**：`/extract`、`web_fetch` 直接抓取调用方给的 URL，公网部署后可被用来探测内网（`http://127.0.0.1:6379`、`http://169.254.169.254/latest/meta-data/` 等）。

**实现**：新增 `src/utf8_search/security.py`，在 `PageExtractor._download` 之前做校验：

- 仅允许 `http` / `https`；
- DNS 解析后校验所有解析结果都不落在保留网段：`0.0.0.0/8`、`10/8`、`127/8`、`169.254/16`、`172.16/12`、`192.168/16`、`100.64/10`、`224/4`、`::1`、`fc00::/7`、`fe80::/10`；
- **重定向必须逐跳复检**（httpx 的自动跟随会绕过校验，需改为手动跟随）；
- 限制重定向次数（默认 5）；
- 新增配置 `UTF8SEARCH_BLOCK_PRIVATE_HOSTS`（默认 `true`，内网自用可关）。

**验收**：新增单测覆盖上述每类地址；`curl /v1/extract` 传 `http://127.0.0.1:8888` 应被拒绝。

**实现结果（2026-09-24，分支 `feature/m4-ssrf-protection`）**：

- 新增 `src/utf8_search/security.py`（协议白名单 + 保留网段 + 内网主机名 + DNS 解析校验）；
- `PageExtractor.extract` 入口校验，`_download` 改为手动逐跳跟随重定向并逐跳复检；
- 新增配置 `UTF8SEARCH_BLOCK_PRIVATE_HOSTS`（默认 true）与 `UTF8SEARCH_MAX_REDIRECTS`（默认 5）；
- 离线测试 `pytest -q -m "not net"` → 69 passed；联网冒烟 4 passed；
- 端到端：本机 / 云元数据 / `file://` 三类地址均返回 `failed_results` 且 0.001 s 返回（未发请求），`https://example.com` 正常抓取不受影响。
- 已知限制：不做 DNS 固定，理论存在 DNS rebinding 时间差窗口。

## 5. M5 详细任务（P1）

### 5.1 引擎健康度自适应（✅ 已完成 2026-09-24）

- 新增 `providers/engine_health.py`：进程内按引擎名维护健康状态（连续失败次数、冷却到期时间、失败原因），
  每次查询动态生成 `engines` 参数。**不是一次性剔除，而是「租约式冷却 + 到期自愈」**：
  - 按失败原因分级冷却：`CAPTCHA` 1800s / `access denied` 900s / `too many requests`·429 180s /
    `timeout` 90s / 其他 120s；连续失败指数退避、封顶 3600s；任一次成功即清零。
  - **覆盖率下限** `engine_health_min_active`（默认 6）：可用引擎不足时按「最早解冻优先」补足，
    引擎集合不会因连锁冷却而萎缩。
  - **空结果不算失败**：只有出现在 `unresponsive_engines` 里的引擎才计失败
    （实测 `zapmeta` / `reloado` 对中文长尾返回 0 条但完全健康）。
  - **502/503/504 重试不再抛弃 `engines`**：旧实现重试时去掉 engines，等于退回 SearXNG 默认引擎集合、
    返回内容脱离本服务控制（实测会混入垃圾农场内容）；现在改为「剔除冷却中引擎」后带约束重试。
  - `/health` 暴露引擎健康快照（冷却中的引擎 / 档位 / 剩余时间 / 原始原因 / 本次实际使用的引擎集合）。

**实测修正了本节的原有前提**（2026-09-24，12 引擎逐引擎隔离实测 + `/metrics`）：

1. **剔除被限流的引擎不会降低延迟**。SearXNG 对惩罚期（suspended）的引擎是*快速失败*：
   单引擎探测 0.03-0.19s、0 条结果，且 `request_count_total` 不增长 —— 根本没往上流发请求。
   配对 A/B（n=24）显示延迟差中位 **−16ms**、自适应更快的比例 62%，即无因果影响。
2. **「按成功率排序」不采用**：引擎顺序对延迟无影响（顺序反转实测 P50 0.91s vs 0.99s，属噪声），
   排序只会让行为不可预测；改为保持候选原序。

**真正的收益是稳健性**（`scripts/bench_engines.py --rounds 3`，24 对配对样本、逐条交替两种模式）：

| 指标 | 静态引擎名单 | 健康度自适应 |
| --- | --- | --- |
| 结果数中位 | 10.0 | 10.0 |
| 上游「不可用引擎」报告次数 | 142 | **0** |
| P50（原始，受上游双峰噪声影响） | 1199 ms | 1146 ms |
| 配对延迟差中位 | — | **−16 ms**（自适应更快的比例 62%） |

判定通过（覆盖率不下降 + 延迟不劣化 + 上游异常次数不增加），详见 `checklist.md` 第 11 节。

- **踩坑（已修）**：`unresponsive_engines` 的文案是按 `Accept-Language` 本地化的。本服务客户端带
  `zh-CN`，实测返回「暂停服务: 请求过于频繁 / 拒绝访问 / 验证码」；只写英文规则会让所有原因落进
  `other` 档（CAPTCHA 只冷却 120s ≈ 反复撞墙）。分类器现同时匹配中英文，未命中则靠指数退避兜住。
- 新增配置：`engine_health_enabled` / `engine_health_min_active` / `engine_health_probe_slots` /
  `engine_health_cooldown_{captcha,denied,rate_limit,timeout,other,max}`；关闭开关完全等价于旧行为。
- 遗留：健康状态是**进程内**的，多副本部署各自学习（如需共享可换 Redis）。
  `/metrics` 本次只用于可观测（它是平均值而非分位数、且只覆盖有请求的引擎），不参与选路。

## 8. 前置条件与风险

- **需要用户提供**：一台可自由出网的云服务器（用于 4.2，暂缺，已暂缓）；是否要立刻做公网部署。
- **风险**：免费引擎的可用性会随上游策略变化，`searxng/settings.yml` 的名单需定期复测（建议每季度跑一次逐引擎实测）。自 5.1 起，引擎临时被限流/封锁已由 `EngineHealthTracker` 自动冷却与恢复，手工维护名单只需关注「长期完全不可用」的引擎（用 `/health` 的 `engines.cooling` 复核）。
- **风险**：公网开放 `extract` 接口前，4.1 必须先做完。
- **已知限制**：`answer`（自带 LLM 摘要）与 `images` 明确不做。
