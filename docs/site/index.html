快速开始

这里是 utf8-search 使用说明站：把仓库里的接入指南、客户端配置包、部署手册整理成按场景查找的页面。 站点是纯前端静态页，随项目一起部署、随 docker compose up -d 启动，不依赖任何外部 CDN 或后端服务。

这是什么

utf8-search 是一个免费、高速的联网搜索服务：对 LLM 客户端提供 MCP（stdio / Streamable HTTP）与 Tavily 兼容的 REST 接口，底层聚合 SearXNG 的免费搜索引擎，不要求任何付费 Key。

30 秒发起一次搜索

# 本机部署（默认只绑回环）
curl -s http://127.0.0.1:8000/v1/search \
  -H "Authorization: Bearer $UTF8SEARCH_KEY" \
  -H "Content-Type: application/json" \
  -d '{"query": "Python 3.13 新特性", "max_results": 5, "search_depth": "basic"}'
# 已有 Tavily 代码：只换 base_url 与 key
from tavily import TavilyClient

client = TavilyClient(api_key="<你的 Key>", api_base="http://127.0.0.1:8000")
results = client.search("Python 3.13 新特性", max_results=5)

三种 Key 传法

  1. Authorization: Bearer <Key>（推荐，MCP 与 REST 通用）；
  2. X-API-Key: <Key>（自定义头）；
  3. 请求体字段 "api_key": "<Key>"（仅 REST /v1/search、/search 支持；MCP 不适用）。

不知道 Key 从哪来、怎么确认 Key 有效？见「服务测试台」页的 API Key 是什么——含来源说明与一键「验证 Key」。

公网访问还必须带白名单内的 Host（例如 your-domain.example，写成你实际部署的域名），否则会被 DNS 重绑定防护拒绝（421）。

1. 先决条件

1.1 启动 SearXNG（搜索聚合后端，必须）

cd C:\Users\<用户名>\Desktop\utf8-search

  • 首次查询需要 20–60 秒加载引擎，期间会返回 502，属正常现象；本服务的基准脚本与客户端会自动重试一次。
  • 健康检查：curl http://127.0.0.1:8888/healthz。

1.2 两种运行模式

3. MCP stdio 接入

所有 stdio 客户端都是「启动一个子进程 + 通过 stdin/stdout 走 MCP 协议」，配置只是外壳不同。

  • Windows 下 command 必须是绝对路径，JSON 里反斜杠要写成 \\；Linux / macOS 下同样用绝对路径（例如 /opt/utf8-search/.venv/bin/utf8-search），但不要带 .exe、也不要用 Scripts/。
  • 通过 env 传配置；注意 stdout 是协议通道，本服务的日志一律走 stderr，不会污染协议。

3.1 Claude Desktop

配置文件：%APPDATA%\Claude\claude_desktop_config.json

{
  "mcpServers": {
    "utf8-search": {
      "command": "C:\\Users\\<用户名>\\Desktop\\utf8-search\\.venv\\Scripts\\utf8-search.exe",
      "args": [],
      "env": {
        "UTF8SEARCH_SEARXNG_URL": "http://127.0.0.1:8888",
        "UTF8SEARCH_TRUST_ENV": "false",
        "UTF8SEARCH_LOG_LEVEL": "WARNING"
      }
    }
  }
}

改完配置需完全退出并重启 Claude Desktop。

3.2 Codex

配置文件：~/.codex/config.toml（本机为 C:\Users\<用户名>\.codex\config.toml）

Windows：

[mcp_servers.utf8-search]
type = "stdio"
command = 'C:\Users\<用户名>\Desktop\utf8-search\.venv\Scripts\utf8-search.exe'
startup_timeout_sec = 60

[mcp_servers.utf8-search.env]
UTF8SEARCH_SEARXNG_URL = "http://127.0.0.1:8888"
UTF8SEARCH_TRUST_ENV = "false"
UTF8SEARCH_LOG_LEVEL = "WARNING"

Linux / macOS（以服务部署在 /opt/utf8-search 为例）：

[mcp_servers.utf8-search]
type = "stdio"
command = '/opt/utf8-search/.venv/bin/utf8-search'
startup_timeout_sec = 60

[mcp_servers.utf8-search.env]
UTF8SEARCH_SEARXNG_URL = "http://127.0.0.1:8888"
UTF8SEARCH_TRUST_ENV = "false"
UTF8SEARCH_LOG_LEVEL = "WARNING"

写完先自检 command 指向的文件真的能启动 —— 最快的办法是直接喂一个 initialize 帧（把 <command 的值> 换成你上面实际写的路径）：

printf '%s\n' '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"probe","version":"0"}}}' | <command 的值>

返回的 JSON 里含 "serverInfo"（例如 "name":"utf8-search"）说明可执行文件与 stdio 通道都正常； 若报 command not found / 路径不存在，就是 command 写错了（Linux 上最常见的是沿用了 Windows 的 Scripts\...exe）。

仓库里还有一条更完整的两通道自检（握手 + 工具发现 + 真实调用，服务端实测 6 项全过）：

# Linux / macOS
.venv/bin/python -u scripts/mcp_selfcheck.py --mode stdio,stdio-raw
# Windows
.venv\Scripts\python.exe -u scripts\mcp_selfcheck.py --mode stdio,stdio-raw

改完 config.toml 需要重启 Codex 会话，否则不会重新拉起 MCP 子进程。

若服务跑在另一台机器上、希望 Codex 走 HTTP：Codex 的 MCP HTTP 传输支持随版本演进，较新版本可直接写：

[mcp_servers.utf8-search-http]
type = "streamable_http"
url = "http://<服务地址>:8000/mcp"

若你的 Codex 版本不支持该 type，改用 stdio + 本地桥接（例如 npx -y mcp-remote http://<服务地址>:8000/mcp），或直接调用 REST（见第 5 节）。

4. MCP over HTTP（Streamable HTTP）

$env:UTF8SEARCH_API_KEYS="test123"
utf8-search serve --host 0.0.0.0 --port 8000
  • 端点：http://<host>:8000/mcp（GET /mcp 返回 400 属正常，MCP 握手走 POST）。
  • 未鉴权时客户端可能显示 Auth: Unsupported / 状态 unknown，属预期而非故障：服务端对未带 Key 的请求返回 401，且不带 WWW-Authenticate 响应头，MCP 客户端因此探测不到 OAuth 端点。判断是否真正连上，看工具有没有列出来（web_search / web_fetch）；HTTP 传输的 Key 走静态 Authorization: Bearer 头（各客户端配置见第 3 节）。
  • 部署到公网域名或反向代理后面时，必须配置允许的 Host，否则返回 421：
$env:UTF8SEARCH_MCP_ALLOWED_HOSTS="search.example.com,1.2.3.4:8000"

Python 客户端示例（MCP SDK v2）：

import asyncio
from mcp import Client

async def main() -> None:
    async with Client("http://127.0.0.1:8000/mcp") as client:
        tools = await client.list_tools()
        print([t.name for t in tools.tools])
        result = await client.call_tool("web_search", {"query": "最新的 AI 政策", "search_depth": "deep"})
        print(result.structured_content["results"][0]["title"])

asyncio.run(main())

7. Tavily 兼容替换

服务返回的字段与 Tavily 保持一致，已有代码通常只需改 base_url：

# 原：client = TavilyClient(api_key="tvly-xxx")
# 现：
import httpx

client = httpx.Client(base_url="http://127.0.0.1:8000",
                      headers={"X-API-Key": "test123"})
resp = client.post("/v1/search", json={"query": "OpenAI API 定价", "max_results": 5,
                                      "search_depth": "advanced"}).json()
Tavily 能力本服务说明
POST /search支持/search 与 /v1/search 等价
POST /extract支持/extract 与 /v1/extract 等价
search_depth支持额外提供更强的 deep
topic / days / time_range支持days 内部换算为 time_range
include_domains / exclude_domains支持—
include_raw_content支持—
answer（自带 LLM 摘要）不做设计上不内置 LLM，摘要交给调用方模型
images（顶层与 results[].images）不做（恒空数组）字段已补齐，按字段遍历的客户端不会 KeyError
results[].favicon不做（恒 null）M6 补齐字段
results[].id支持<request_id>-<序号>，可用于去重/引用
response_time / request_id / auto_parameters / usage支持usage.credits 恒 0（本服务免费）；auto_parameters 回显实际生效的 topic/search_depth
未实现的 Tavily 参数（chunks_per_source、start_date/end_date、country、language、safe_search、exact_match 等）接受但忽略直接换 base_url 的客户端不会因多传参数而报错

逐字段对照矩阵（含错误码与限流语义、有意保留的差异与理由）： docs/reports/m6-tavily-compat-20260928.md； 官方字段清单与示例响应留档：docs/reports/tavily-official-search-20260928.md。

1answer 恒 null（本服务不自带 LLM）include_answer=true 时字段存在但为 null；false 时该键不出现（与 Tavily 习惯一致）不要期待一段摘要文本需要摘要就用你自己的模型对 results[].content 再生成

3results[].id 格式不同形如 <request_id>-<序号>（Tavily 是不透明短 id）不要解析它的内部结构只当字符串 id 用（去重/引用都够）
4score 量纲不同本地融合分（引擎权重 + 时效 + 去重）；自 2026-09-30（P7）起 score 保持原始相关性分，排序位序由内部 score × 形态乘子 决定不要与 Tavily 的分数横向比较、不要套阈值；不要假设数组位序与 score 单调一致score 只当同一响应内的相关性参考；要保留我们的排序就直接用数组顺序，不要用 score 自行重排

6response_time 是数字例如 2.5（官方文档"示例响应"里写成字符串 "1.67" 是笔误，其 schema 类型是 number）不要按字符串处理直接当数值；若要两种都兼容用 float(x)
7未实现的 Tavily 参数被忽略chunks_per_source、start_date/end_date、include_published_date、filter_by_published_date、include_image_descriptions、include_favicon、include_domains_mode、country、language、filter_by_language、auto_parameters、exact_match、safe_search 传了不报错不要期待它们生效需要过滤请用已实现的 time_range / include_domains / exclude_domains / topic=news；语言固定 all（中英兼顾）

排序位序不再与 score 单调一致（P7 起）：score 保持原始相关性分（对外语义不变），排序在内部按 score × 形态乘子 计算（对「含实质内容的首页/栏目页」轻微降权），以让独立文章更靠前 —— 因此不要用 score 自行重排结果，要保留我们的排序就用数组顺序。

另外三条与"预期"相关的边界（同一份报告 §1/§3 有完整说明）：

  • search_depth 只接受 basic / advanced / deep（没有 fast/ultra-fast）、max_results 上限 20； 越界与其它参数非法一律返回 400（已对齐 Tavily，官方 SDK 会抛 BadRequestError）；
  • 错误体：我们保持 detail 为字符串（Tavily 是 detail.error），但额外给了顶层 error 可读消息； 429 继续带 Retry-After。官方 SDK 对这种 detail 形态有 try/except 兜底、不会崩。
  • MCP 客户端面板里的 Auth: Unsupported / unknown：见第 4 节的说明，看工具有没有列出来判断连通性；

关于校验错误码的统一 400（决策）：官方错误表里「语义非法」是 400、而「形状校验失败」的示例标的是 422； 我们不做「形状 422 / 语义 400」的逐类分流，统一返回 400。理由：① 官方 SDK 里没有 422 分支， 真 Tavily 的形状错误同样走 raise_for_status() 通用分支 —— 统一 400 是超集行为，不会打断任何在 真 Tavily 上跑得通的客户端；② 分类依据脆弱：形状与语义边界模糊（topic 缺字段 vs 值写错同属 Literal 校验）， 分流要按 pydantic 的 type 字符串硬编码归类，每加字段都要重判；③ 收益只对「照官方 422 示例写死状态码」的 客户端有效，这类客户端基本不存在。将来若确有客户端要求，改一处异常处理器即可 （详见 docs/reports/m6-tavily-compat-20260928.md §7 与 docs/04 §8 遗留任务）。

8. 鉴权与限流

  • 鉴权：配置了 UTF8SEARCH_API_KEYS 才启用；GET /health 不需要鉴权。
  • 三种传 Key 方式：Authorization: Bearer <key>、X-API-Key: <key>、请求体里的 api_key 字段。
  • 限流：滑动窗口，按 Key 计；超限返回 429。UTF8SEARCH_RATE_LIMIT_RPM=0 表示不限。
  • 未配置 Key 时服务会打印告警：HTTP 接口处于开放状态，不要直接暴露到公网。

import asyncio
import sys

from mcp import ClientSession
from mcp.client.stdio import StdioServerParameters, stdio_client


async def main() -> None:
    params = StdioServerParameters(
        command=sys.executable,  # 也可写 utf8-search.exe 的绝对路径
        args=["-m", "utf8_search", "stdio"],
        env={"UTF8SEARCH_SEARXNG_URL": "http://127.0.0.1:8888"},

        async with ClientSession(read, write) as session:
            await session.initialize()
            print([tool.name for tool in (await session.list_tools()).tools])
            result = await session.call_tool(
                "web_search", {"query": "2026年 新能源汽车 补贴政策", "max_results": 5}
            )
            for item in result.structured_content["results"]:
                print(item["title"], item["url"])


asyncio.run(main())

11. 常见问题

Q1：本机 SearXNG 返回 502 / 页面抓取全部超时 Windows 上若开启了系统代理（Clash / V2Ray 等），httpx 会把回环请求也发给代理并收到 502。本服务默认让 127.0.0.1,localhost,[::1],searxng 绕过代理直连。 若本机代理本身不稳定（表现为外网抓取也大面积超时、curl https://example.com 也卡住），把环境代理整个关掉改用直连：

$env:UTF8SEARCH_TRUST_ENV="false"     # 忽略系统/env 代理，全部直连

注意：Docker 里的 SearXNG 不读取 Windows 系统代理，它走容器自己的出口（实测与美国代理出口同一 IP）。因此本机 httpx 抓取失败、而 SearXNG 仍能返回结果，是「宿主代理与容器出口不一致」的典型表现——此时优先怀疑宿主侧代理。

反之，若本机只有「HTTP 代理模式」的 VPN、关掉代理就出不了网，则显式指定：

$env:UTF8SEARCH_HTTP_PROXY="http://127.0.0.1:7897"

Q2：MCP over HTTP 返回 421 配置 UTF8SEARCH_MCP_ALLOWED_HOSTS，填入实际访问用的 Host（域名或 IP:端口）。 未配置时 MCP SDK 只放行本机 Host（127.0.0.1 / localhost / [::1]），因此从另一台机器用 http://192.168.x.x:8000/mcp 访问也会被 421 拒绝 —— 把 192.168.x.x:8000 加进白名单即可。 （自检脚本里「伪造 Host → 421」验证的就是这条防 DNS 重绑定防护。）

Q3：首次调用很慢或失败 SearXNG 冷启动需要 20–60 秒加载引擎；先 curl http://127.0.0.1:8888/healthz 确认就绪。

Q4：结果条数变少、failed_engines 里有引擎名 原因通常是 SearXNG 容器没起来或引擎名单被改坏，而不是引擎不够用。本服务默认配置了 13 个实测可用引擎（searxng/settings.yml 里 keep_only + disabled: false 双重配置），单次查询可拿 80+ 条原始结果。 排查顺序：① curl http://127.0.0.1:8888/healthz 是否 200；② curl "http://127.0.0.1:8888/search?q=test&format=json" 是否有 results；③ 逐引擎单测：engines=<名字>，且不要同时传 categories（两者会叠加，显式引擎列表会失效），否则不能凭「返回了结果」判断该引擎可用。 少数机会型引擎（reloado / yep / brave / quark）会间歇被限流，失败极快、代价可忽略；若全部失效，服务会自动降级到 Bing HTML 直取兜底，并在 engines_used / failed_engines 中如实上报。

Q5：deep 模式有多快、读多少页 实测（美国出口 IP，冷启动缓存）：deep P50 ≈ 9.2 s，平均读取 16.2 个页面（单次 14–19 页）；advanced P50 ≈ 3.8 s（读 3 页）；basic P50 ≈ 1.0 s。详见 docs/01 第 5 节。

Q6：/extract 返回 failed_results，提示「属于保留网段」/「不允许访问」 这是 SSRF 防护在生效：默认拒绝抓取内网与保留地址（127.0.0.1、10.x、192.168.x、169.254.169.254 等）以及 localhost、.internal 等内网主机名，只放行 http/https。公网部署请保持开启。 若你确实在内网环境自用（例如抓内网 wiki），可显式关闭：

$env:UTF8SEARCH_BLOCK_PRIVATE_HOSTS="false"

关闭后请不要把服务暴露到公网；该开关只影响 /extract 与 web_fetch 的抓取校验。UTF8SEARCH_MAX_REDIRECTS 可改重定向跳数上限（默认 5）。

要不要把上限调大（例如 6）？（详见 docs/reports/m5-concurrency-gate-20260927.md）

  • 上游健康的日子（能稳定跑 ~4 req/s）默认 3 会多付约 20-30% 的尾延迟/墙钟： 并发 10 实测 P50 2.4-2.6s → 3.2-3.4s、墙钟 13.4-13.8s → 16.5-17.6s。若你的上游长期稳定、 更在意延迟，可以把上限调到 6。
  • 风险：上限一旦超过上游真实容量，就回到「全体一起慢」——实测并发 30 打爆上游时单请求会飙到 10-12s（连接异常 + 本地重试各 5.5s）。调大后请用 scripts/loadtest.py 复测，并盯 /metrics 的 utf8search_upstream_requests_total{result="error"}：> 0 就说明已经打爆。
  • news 的补充路只在主源不足时才触发（判据：主源凑不满 max_results），所以多数 news 请求只打 1 路上游； 需要补时是串行两跳。UTF8SEARCH_UPSTREAM_OPTIONAL_WAIT（默认 1.0s）是这条兜底路取容量的等待上限 —— 拿不到容量就直接 429，绝不静默跳过（跳过会把中文长尾的空结果交给用户，是质量事故）。 重扫 1.0 / 1.5 / 3.0s：news@10 降级率 0%、空结果率 0%、P95 5.96 / 6.43 / 6.10s → 取最小 1.0s。
  • news@30 的“净负”是好日 artifact：交错复测（base→gate→base→gate，各 2 轮）显示——健康日基线能 100% 服务、 只是尾延迟 6.5-9.6s，而闸门把 80-85% 的请求变成 429（成功率 15-20%）、把服务到的请求 P95 压到 4.9-6.6s。 也就是说好日子里 news@30 用闸门得不偿失（没有坏日要防）。 坏日（上游被打爆、docs/04 §4.4 记录的单请求 19s 级）闸门才是保护：它把“全体一起慢”换成“多数快速失败 + 少数可控”。
  • news 高并发的扩容方向（而不是调闸门参数）：
    1. 多实例 SearXNG + 前置负载均衡：闸门上限是单进程、单上游的，加实例才能提高总容量（limit 可按实例数分摊）；
    2. 只在确认上游余量时提高 MAX_CONCURRENCY：判据是 /metrics 里 utf8search_upstream_requests_total{result="error"} 长期为 0 且上游 P95 稳定；一旦出现 error 或 单请求回到 10-12s，说明已经超过真实容量，必须调回；
    3. news 为主时优先保证 OPTIONAL_WAIT（兜底路）而不是主源并发——news 的召回依赖那一路， 牺牲它换来的是空结果而不是速度。
  • 指标：GET /metrics（沿用 REST 鉴权，需带 Key）暴露 upstream_active / waiting / rejected_total{reason} / 排队与上游延迟直方图，排障时先看 rejected_total 的 reason 构成。

docker compose exec -T caddy sh -c "rm -rf /data/caddy/certificates/local/203.0.113.10.sslip.io"
docker compose restart caddy
docker compose logs caddy --since 5m | grep -iE "obtaining certificate|challenge failed|certificate obtained"
# 期望：certificate obtained successfully ... issuer ... acme-v02.api.letsencrypt.org-directory

该流程先在安全组未放行时预演过：删证书 + 重启后 Caddy 确实重新走了一遍 ACME （http-01 / tls-alpn-01 均因超时失败），随后回退到自签、服务全程 200 不中断。 2026-09-25 安全组放行后照此执行即签发成功，拿到受信任真证书（见 5.1）。

5.4 续期（依赖 80/443 长期放行，否则 3 个月后静默失效）

Caddy 全自动：到期前 30 天开始续，证书与 ACME 账号存放在命名卷 utf8-search_caddy_data。

关键：续期和首次签发走的是同一条路 —— Let's Encrypt 必须能从公网回连本机 80（HTTP-01）或 443（TLS-ALPN-01）。因此安全组 22/80/443 必须长期放行，不能只在首次部署时临时开一下。

后果很隐蔽，务必记住：

  • 若在证书到期前把 80/443 关掉，续期会在后台反复失败，Caddy 不会主动告警；
  • 旧证书一过 2026-12-24，所有客户端都会看到「证书已过期」而直接拒绝连接，服务等于中断；
  • 本证书建议在 2026-11-24 前后主动核对一次续期是否成功（Caddy 提前 30 天就该续好）。

核对方式：

# 证书到期日应从 2026-12-24 变成新的日期；issuer 仍是 Let's Encrypt
echo | openssl s_client -connect 203.0.113.10.sslip.io:443 \
  -servername 203.0.113.10.sslip.io 2>/dev/null | openssl x509 -noout -dates -issuer
# 续期日志（成功会打 "certificate obtained"）
docker compose logs caddy --since 24h | grep -iE "certificate obtained|renew|error"

不要删这两个卷，否则每次重启都会重新签发，容易撞 Let's Encrypt 配额：

docker volume ls | grep caddy      # utf8-search_caddy_data / utf8-search_caddy_config

5.5 自签兜底时的客户端信任方式（当前未使用，留作应急）

自签证书由 Caddy 内置 CA 签发，客户端需信任该根证书。根证书在容器内： /data/caddy/pki/authorities/local/root.crt。

# 导出到宿主机（data/ 被 gitignore，不会进仓库）
docker compose exec -T caddy cat /data/caddy/pki/authorities/local/root.crt > data/caddy-local-root.crt

# 方式 A：装进系统信任库（推荐，curl / 浏览器 / Python(truststore) 都生效）
cp data/caddy-local-root.crt /usr/local/share/ca-certificates/utf8-search-caddy-local.crt
update-ca-certificates

# 方式 B：只在单条命令里信任
curl --cacert data/caddy-local-root.crt https://203.0.113.10.sslip.io/health

# 方式 C：只信任一次、不校验（仅排障，不要用在真实客户端）
curl -k https://203.0.113.10.sslip.io/health

注意两点：

  • Python httpx 分两种行为：httpx.AsyncClient(trust_env=False)（本项目自检脚本用的就是这种） 只认 certifi 的 CA 包、不认系统信任库； 而 MCP SDK 的 HTTP 客户端走 truststore，只认系统信任库。两者都要覆盖才跑得通 —— 这也是当初优先把 ACME 修好（换成真证书）的原因；上面的应急流程只在前者失效时用。
  • 自签证书有效期很短（Caddy 内部 CA 默认 12 小时）并由 Caddy 自动轮换，客户端信任的是根证书（10 年）。

5.6 应急：退回自签后如何换回真证书

8. 常见故障排查

8.1 查询返回 0 条 = 引擎不可达（最常见）

按下面的顺序逐层排除，不要直接改代码：

# 第 0 层：服务自己怎么说
curl -sS http://127.0.0.1:8000/health | python3 -m json.tool
#   看 status / searxng / engines.cooling / engines.active

# 第 1 层：容器在不在
docker compose ps

# 第 2 层：SearXNG 直连有没有结果
curl -sS "http://127.0.0.1:8888/search?q=test&format=json" | head -c 300

# 第 3 层：单引擎隔离，看 unresponsive_engines 的原因
curl -sS "http://127.0.0.1:8888/search?q=AI+news&format=json&engines=google%20news" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); print(len(d['results']), d.get('unresponsive_engines'))"

# 第 4 层：服务器本身能不能出网
curl -sS -o /dev/null -w "%{http_code} %{time_total}s\n" https://www.google.com
curl -sS -o /dev/null -w "%{http_code} %{time_total}s\n" https://duckduckgo.com
curl -sS -o /dev/null -w "%{http_code} %{time_total}s\n" https://www.bing.com

排查结论对照表：

现象判定处理
/health 的 searxng=unreachable服务/依赖问题docker compose ps 看 searxng 是否 healthy；docker compose logs searxng
SearXNG 直连 0 条、unresponsive_engines 全是 Timeout/ConnectTimeout出网/引擎不可达跑第 4 层；若三站都不通，是服务器出网问题（安全组出方向 / DNS / NAT）
SearXNG 直连 0 条、unresponsive_engines 是 Suspended: CAPTCHA / access denied多为 SearXNG 处罚盒自锁，不一定是 IP 被封先 docker compose restart searxng 清空处罚盒，等 40 秒再隔离测一次；可用引擎集合见 /health 的 engines.active
SearXNG 直连正常、应用 0 条服务问题看应用日志；确认 UTF8SEARCH_DEFAULT_ENGINES / NEWS_ENGINES 配置
/health 返回 403 或 JSON 被拒SearXNG settings.yml 未开 formats: [html, json]检查挂载了哪份 settings（见 4.2）

关于引擎处罚盒（重要，4.2 部署实测踩过）：SearXNG 内部对失败引擎有"暂停"机制。一旦某引擎（典型是 google / google news） 被判为机器人，SearXNG 会在处罚期内直接返回 Suspended: CAPTCHA，根本不向上游发请求。此时 /health 会给出 class=captcha、reason=暂停服务: 验证码、consecutive_failures 与 retry_after。

所以「连续多轮 100% 失败」几乎都是SearXNG 自己的处罚盒还没到期，不要据此判定「这台机器的 IP 被 Google 封了」。 4.2 部署当天的证据链：同机同 IP，google news 连续 6/6 失败（Suspended: CAPTCHA），但 docker compose restart searxng 清空处罚盒后立刻 6/6 成功；同机直连 https://www.google.com/search?q=test 也稳定 200、无风控页。

排障动作固定为两步，顺序不能反：

docker compose restart searxng     # 第 1 步：清空 SearXNG 处罚盒
# 等 40 秒引擎加载
curl -sS "http://127.0.0.1:8888/search?q=AI+news&format=json&engines=google%20news" \
  | python3 -c "import json,sys; d=json.load(sys.stdin); print(len(d['results']), d.get('unresponsive_engines'))"
# 第 2 步：隔离测（只看 unresponsive_engines 的真实原因，别被处罚盒误导）

BACKUP_SKIP_CACHE=1 bash scripts/backup.sh /var/backups/utf8-search/deploy-backups-<日期>   # 跳过可重建的 SQLite 缓存
bash scripts/backup.sh                                                  # 全量（含 cache.db ~12MB）
  • 默认加密：backup.sh 产出 utf8-search-backup-<日期>.tar.gz.enc（AES-256-CBC + pbkdf2 200k 迭代）， SHA256SUMS 记的是密文的校验和；口令只从环境变量/口令文件读，缺口令直接拒绝执行 （要明文必须显式 --allow-plaintext，不推荐）。口令来源二选一：
  export BACKUP_PASSPHRASE='<强口令>'                    # 交互场景
  BACKUP_PASSPHRASE_FILE=/etc/utf8-search/backup.pass  # cron 场景：600 权限文件（当前服务器已配置）

⚠️ 口令保管：口令文件不进备份、不写日志，必须与备份分开保存（异机密钥库 / 密码管理器）； 口令丢失 = 备份不可恢复（没有后门路径）。

  • 必须备份：.env（机密：API Key / Host 白名单）、docker-compose.yml、Caddyfile、 searxng/settings.yml + settings.local.yml、data/（缓存 + 测量产物 + 长稳 CSV/JSON + 巡检日志）。
  • 打包产物：…tar.gz.enc（600）+ SHA256SUMS，目录权限 700；异地上传前可再叠一层加密（age/gpg）。
  • 解密恢复步骤：
  cd <备份目录>
  sha256sum -c SHA256SUMS                      # 先验密文完整性
  openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 -pass env:BACKUP_PASSPHRASE \
      -in utf8-search-backup-<日期>.tar.gz.enc -out restore.tar.gz
  gzip -t restore.tar.gz && tar -xzf restore.tar.gz -C /tmp/restore   # 解到临时目录，不要覆盖现网
  cd /tmp/restore/utf8-search && docker compose config >/dev/null       # 解析校验
  • 恢复演练（不要在现网直接演练）：解包到 /tmp → sha256sum -c SHA256SUMS → docker compose config 解析 → 比对 .env 键集合。 实测结果见 docs/reports/m6-ops-hardening-20260930.md（明文版）与 docs/reports/20260930-p3-backup-encryption.md（加密版）。

14.7 ⚠️ 不要启用多 worker

上游并发闸门（upstream_max_concurrency=3）是进程内计数器。若用 uvicorn --workers N 或多容器横向扩， 每个 worker 各自持有 limit，全局并发 = N × limit，等于把"保护上游"的设计废掉； 真要多 worker，必须先按 worker 数分摊 limit（例如 3 个 worker 时每个设 1），或把闸门改成共享存储（Redis）版本。

14.8 备份保留策略的排除名单与"永不删光"（2026-10-01 加固）

  • BACKUP_EXCLUDE（空格分隔）列出永不参与清理的目录名/glob。默认 deploy-backups-20260929 —— 那台服务器上的这个目录装的是人工回滚资产（.env 备份、compose 快照、历史镜像/容器 JSON、压测与自检证据）， 不是 backup.sh 的自动产物；保留策略必须跳过它（P8 修正版会 rm -rf 整目录，代价不可接受）。 例：BACKUP_EXCLUDE="deploy-backups-20260929 deploy-backups-manual-*"。
  • 永不删光保险：每次清理前先算出最新一份产物（按 mtime），它本身、它的 SHA256SUMS、它所在目录 一定不会被删（即使全部超期）。日志里会打印 （保险）最新产物不会被删：<路径>。
  • 清理范围仍是 BACKUP_ROOT（默认 /root）下的 deploy-backups-*，按 mtime；依旧先打印清单再删。
  • ⚠️ cron 跟随当前签出的分支：cron 执行的是 /opt/utf8-search/scripts/backup.sh， 所以脚本内容取决于仓库当时 checkout 的分支。实测 2026-10-01 03:30 的自动备份产出的是明文包 （当时工作区不在本分支上）。在把本分支合并进 main 之前，cron 行为不可依赖； 已把当天明文包重加密并销毁明文（见 docs/reports/20261001-backup-retention-hardening.md）。

服务测试台（节点 / 调试）

API Key 是什么？

  • 它是什么：本搜索服务的访问凭证，由部署者在服务端配置 UTF8SEARCH_API_KEYS=key1,key2（逗号分隔、可多个；留空 = 关闭鉴权）。 说明站本身是静态页面，不需要 Key——Key 只用于直连搜索 API。
  • 什么时候要：GET /health 返回 auth_enabled=true 时必须带 Key，否则 401； MCP 的本地 stdio 通道免 Key（本机可信），HTTP/HTTPS 通道与 REST 一样要带。
  • 去哪里拿：自己部署 → 看服务器的 .env（UTF8SEARCH_API_KEYS，或部署时你自己设的值）； 用别人的服务 → 找服务提供者申请。本站不保存、不展示任何 Key。
  • 怎么传（三选一）：Authorization: Bearer <key>（推荐，MCP/REST 通用）、 X-API-Key: <key>、请求体 {"api_key": "<key>"}（仅 REST）。MCP 只支持前两种请求头。
  • 报错怎么读：401 = Key 缺失/错误；429 = 触发限流（默认每 Key 60 次/分钟）， 看 Retry-After 等几秒再试；/health 不需要 Key，可先用它确认服务是否开了鉴权。
  • 安全：Key 等同密码，别提交进仓库或贴到公开页面；测试台的「记住」只写本标签页 sessionStorage，关掉标签页即失效。
