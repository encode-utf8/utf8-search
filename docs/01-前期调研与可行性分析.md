# 01 前期调研与可行性分析

> 项目：utf8-search —— 面向 LLM 的免费、高速联网搜索服务
> 阶段：M1/M2 已实现并完成实测验收（详见 `checklist.md` 第 6 节实测记录）
> 调研日期：2026-09-23

## 1. 调研目标

1. 验证「免费 + 高速」是否同时成立：在不购买任何商业搜索 API 的前提下，能否做到接近 Tavily / DeepSeek 联网搜索的效果。
2. 确定主力搜索源、兜底源，以及各引擎在当前网络环境下的真实可用性。
3. 用实测数据找出性能瓶颈，给出可量化、可验收的延迟预算。
4. 明确合规、稳定性与工程落地风险。

## 2. 结论速览

- **免费可行**：`自建 SearXNG（多引擎聚合）+ 本地正文抽取 + 多级缓存` 可实现零边际成本运行，不依赖任何付费 Key。
- **高速可行**：M2 实测（冷启动、清空缓存）basic P50 **1048 ms**、advanced P50 **3775 ms**、deep P50 **9234 ms**，与 DeepSeek 联网搜索同档位。前提是必须做预热、并发、硬超时、缓存四项优化，否则最慢页面会把一次请求拖到 28 s（调研期实测）。
- **「读几十个网页」可行**：deep 模式平均读取 **16.2** 个页面（单次 14–19 页），P50 约 9.2 s，一次查询可拿到 80+ 条原始结果。
- **免费引擎足够多，无需降级**：逐引擎实测后有 **9 个稳定可用** + **4 个机会型**引擎（含 Google、Sogou、Yandex、PrivacyWall、Resulthunter、Zapmeta、Yep 等），不必依赖单一引擎或兜底源。详见 4.3。
- **必须先解决性能瓶颈**：真正拖慢整体的是**正文解析（trafilatura，受 GIL 限制）**而非下载；解析线程池并非越大越快（详见 4.5）。
- **必须自建**：10 个公开 SearXNG 实例实测全部关闭 JSON 接口或被限流，不可依赖。
- **最大不确定性**：反爬与上游限流。机会型引擎会随时被限流，因此架构上仍需保留「多引擎冗余 + 可插拔 + 自动降级 + 兜底源」。

**结论**：同时满足「零边际成本 + 可自托管 + 可服务任意 LLM」的技术路线只有一条——**自建 SearXNG 聚合 + 本地抽取重排**；上述商业 API 全部降级为「可选增强」（配置 Key 即启用，不配置也能跑）。

### 4.3 自建 SearXNG 的引擎级可用性（2026-09-24 逐引擎实测）

**踩坑记录（重要）**：SearXNG 的 `engines` 查询参数会**静默丢弃未启用/不存在的引擎**，全部无效时还会**回退到默认引擎集**。早期用 `engines=mojeek` 仍返回 22 条结果，看似 mojeek 可用，实则是「参数被忽略 + 回退默认」造成的假象。**判断引擎是否可用，必须逐引擎单独实测。**

**另一处关键踩坑**：只配 `keep_only` 是不够的——它只做名单过滤，**不改变引擎自身的默认启用状态**（本镜像里 bing / google / duckduckgo / sogou / yandex / naver 默认都是 `disabled`）。必须再用 `engines:` 列表逐条 `disabled: false` 打开。

**本镜像中被标记 `inactive: true` 的引擎**（无法启用，`keep_only` 也不会匹配到，所以会从 `/config` 里彻底消失）：

| 引擎 | 原因 |
| --- | --- |
| `mojeek` | 改用 Proof-of-Work 验证码，`inactive: true` |
| `startpage` | 改用 Proof-of-Work 验证码，`inactive: true` |
| `dogpile` / `swisscows` / `luxxle` / `findborg` 等 | 同上，`inactive: true` |

**最终实测结果**（5 条中英查询交叉验证，美国出口 IP）：

| 引擎 | 结果数（各查询） | 结论 |
| --- | --- | --- |
| `resulthunter` | 20 / 19 / 20 / 20 / 20 | ✅ 稳定 |
| `yandex` | 15 / 15 / 15 / 15 / 15 | ✅ 稳定 |
| `naver` | 15 / 15 / 15 / 15 / 15 | ✅ 稳定 |
| `privacywall` | 10 / 10 / 10 / 10 / 10 | ✅ 稳定 |
| `google` | 10 / 10 / 10 / 10 / 10 | ✅ 稳定（⚠️ 早期因网络层问题被判为「需 JS 渲染」，实为误判） |
| `zapmeta` | 9 / 9 / 9 / 9 / 9 | ✅ 稳定 |
| `yahoo` | 7 / 7 / 7 / 7 / 7 | ✅ 稳定 |
| `fynd` | 3 / 10 / 10 / 10 / 10 | ✅ 稳定 |

| `reloado` | 24 / 30 / 12 / 5 / 0 | 🔶 机会型（产量高但不稳定） |
| `yep` | 0 / 20 / 0 / 20 / 0 | 🔶 机会型 |
| `brave` | 20 / 0 / 0 / 0 / 0 | 🔶 机会型（易被限流，失败仅 0.02 s） |
| `quark` | 0 / 9 / 0 / 0 / 0 | 🔶 机会型（夸克搜索，常触发 CAPTCHA） |
| `bing` | 0 / 0 | ❌ 经 SearXNG 返回 0 条 |
| `duckduckgo` | 0 / 0 | ❌ CAPTCHA |
| `google cse` | 0 / 0 | ❌ `unusual traffic`，账号级封禁 |
| `baidu` / `qwant` | 0 / 0 | ❌ CAPTCHA |
| `seznam` | 0 / 0 | ❌ timeout |
| `crowdview` / `fastbot` / `tusksearch` / `vuhuv` / `fireball` / `gabanza` / `searchmysite` / `ayo` / `encyclosearch` / `abcnyheter` | 0 | ❌ 返回 0 条或超时 / SSL 错误 / access denied |

**工程结论**：

1. 免费引擎完全够用：**13 个引擎**同时查询，一次请求可拿 **80+ 条原始结果**（实测 81 条 / 10 个引擎命中）。
2. 必须 `keep_only` + `disabled: false` 双重配置。
3. 必须设置 `outgoing.request_timeout: 8.0`（默认 3 s 会让略慢的引擎超时，而引擎超时可能触发 SearXNG 的 `add_unresponsive_engine after close` 异常并把 worker 打挂，表现为 502）。
4. 机会型引擎失败极快（0.02–0.4 s），**保留它们几乎零成本，命中则显著增益**。
5. `wikipedia` / `wikidata` 默认启用但会超时并打挂 worker，已排除。

### 4.4 抓取与抽取实测

对一次查询的 6 个结果页做并发抓取（无超时保护）：

| 页面 | 耗时 | 大小 |
| --- | --- | --- |
| openai.com/api/pricing | 1002 ms | 抓取失败（-1） |
| metacto.com 博客 | 1362 ms | 228 KB |
| cloudzero.com 博客 | 1373 ms | 201 KB |
| developers.openai.com 文档 | 1460 ms | 576 KB |
| benchlm.ai | 3133 ms | 187 KB |
| azure.microsoft.com 价格页 | 15083 ms | 1311 KB |
| **整体（并发）** | **28646 ms** | 6 页 |

**关键结论**：5 / 6 的页面在 3.1 s 内就绪，但整体被最慢的 1.3 MB 页面拖到 28.6 s。因此**必须设置单页硬超时 + 结果数量阈值提前返回**，否则延迟不可控。

### 4.5 抓取与解析分段实测（M2 性能调优依据）

对 22–24 个真实结果页并发测试：

| 阶段 | 耗时 | 说明 |
| --- | --- | --- |
| 并发下载（22 页） | 3.41 s | 最慢单页 2.99 s，**下载不是瓶颈** |
| 并发解析（19–21 页，串行） | 3.89 s | 平均 0.19 s/页 |
| 并发解析（19 页，32 线程） | 5.36 s | 线程池越大反而越慢 |
| 并发解析（19 页，2 线程） | 4.83 s | 实测最快档位 |

**关键结论（本项目最重要的性能发现）**：trafilatura 的正文抽取是受 **GIL 限制**的纯 Python 计算，线程池规模并非越大越快；实测 2–8 线程最佳，32 线程会因争抢 GIL 让单页解析从 0.13 s 恶化到 **11 s**。据此做了三项优化：

1. `UTF8SEARCH_EXTRACT_WORKERS` 默认由 32 下调到 **8**。
2. 搜索结果本身已带标题时**跳过 `extract_metadata`**——那是一次与正文抽取等价成本的完整解析，白白翻倍耗时。
3. deep 模式的提前返回阈值 `UTF8SEARCH_DEEP_EARLY_STOP_RATIO` 提高到 **0.8**（覆盖优先，对标「读几十个网页」）。

## 5. 延迟预算与实际结果

设计目标：

| 阶段 | 调研期实测 / 预估 | 目标 |
| --- | --- | --- |
| 查询聚合（预热后的 SearXNG） | 1.1 s | ≤ 1.2 s |
| RRF 融合 + 去重 | < 10 ms | ≤ 20 ms |
| 结果页并发抓取（硬超时保护后） | 3.1 s（无保护时 28.6 s） | ≤ 3.0 s |
| 正文抽取（trafilatura 并行） | 0.2 s/页（GIL 限制，见 4.5） | ≤ 1.0 s |
| 缓存命中路径 | — | ≤ 50 ms |

**M2 实测（`python scripts/bench.py --n 5 --fresh`，冷启动、清空缓存）**：

| 模式 | P50 | P90 | P95 | 最大 | 平均读页 | 目标达成 |
| --- | --- | --- | --- | --- | --- | --- |
| basic | 1048 ms | 1095 ms | 1095 ms | 1544 ms | 0 | ✅ P50 ≤ 1.5 s，P95 ≤ 3 s |
| advanced | 3775 ms | 3914 ms | 3914 ms | 4492 ms | 3.0 | ✅ P50 ≤ 4 s，P95 ≤ 8 s |
| deep | 9234 ms | 9492 ms | 9492 ms | 10462 ms | 16.2（14–19 页） | ✅ 平均读页 ≥ 15 |

> 聚合上限 `UTF8SEARCH_SEARCH_TIMEOUT_LIMIT` 由 4.0 s 收到 **2.5 s**：实测 2.0/3.0/4.0 s 三种上限都能拿满结果（结果集早已饱和），收到 2.5 s 只是砍掉长尾，basic P50 从 2056 ms 降到 1048 ms。

> 注：以上为网络正常时段的测量值。免费引擎被限流或本机 VPN 出口异常时，服务会自动降级到 Bing HTML 兜底源，延迟会上升到 4–9 s。

## 6. 可行性结论

### 6.1 免费可行性：成立

- 搜索：自建 SearXNG（Docker 官方镜像，已验证可拉取运行）+ Bing HTML 直取兜底，零费用。
- 抽取：本地 `httpx` + `trafilatura` 完成；失败时用免密钥的 Jina Reader 兜底，零费用。
- 缓存与重排：SQLite + BM25 本地完成，零费用。
- 商业 API（Brave / Google CSE / Serper / Tavily）仅作为可选增强，缺省不启用也能正常服务。

### 6.2 高速可行性：成立，但有前提

达到 1–10 s 级响应需要同时满足：① SearXNG 常驻并预热；② 多引擎并发由 SearXNG 内部完成；③ 抓取阶段硬超时 + 提前返回；④ 三级缓存（查询 / 正文 / 结果包）；⑤ 解析线程池规模要小（GIL 限制，见 4.5）。

### 6.3 工程可行性：成立

- Docker 29.6.1 可用，SearXNG 官方镜像已实测跑通并返回结构化 JSON。
- MCP 侧：PyPI `mcp` 2.2.0（v2 稳定线，含 stdio 与 Streamable HTTP 传输）已实测双通道可用。
- 交付形态：单个 MCP Server 进程 + 一个 SearXNG 容器，`docker compose up` 可一键起。

### 6.4 风险与限制

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 引擎被上游限流 | 机会型引擎（reloado / yep / brave / quark）会间歇失效；bing / duckduckgo / google cse / baidu 已确认不可用 | 13 引擎冗余、`failed_engines` 上报、失败极快零成本、自动降级到 Bing 兜底源、多级缓存 |
| 抓取超时拖慢 | 实测最慢页面 15 s | 硬超时 + 数量阈值提前返回 + 并发上限 |
| 解析 GIL 瓶颈 | 大线程池反而拖慢单页解析 | 线程池下调到 8、跳过冗余的 metadata 解析 |
| JS 渲染页面 | 静态抓取拿不到正文 | 默认跳过，可选 Playwright（慢，按需开启），Jina Reader 兜底 |
| 公开实例不可用 | 10 个实例全部失效 | 自建 SearXNG（本次已验证） |
| 本机网络环境 | 开发期出现系统代理失效导致外网全超时 | 提供 `UTF8SEARCH_TRUST_ENV=false` 直连开关；部署到服务器无此问题 |
| 合规 | 抓取公开网页的 ToS / robots 问题 | 遵守 robots.txt、限速、只抓公开页面、不绕过付费墙、不转售原始数据 |
