# M5 上游并发闸门 + 过载快速返回 验收报告（2026-09-27）

- 分支：`feature/m5-concurrency-gate`（基于 `main` @ `5f16f28`）
- 背景：`docs/04` §4.4 实测——并发 1-3 时 P50 ≈ 1.3s，并发 10 冷查询劣化到 ~12s；直连 SearXNG 探测显示
  上游聚合吞吐仅 1.3-2.0 req/s，**瓶颈在上游聚合而非本服务**。
- 策略（本轮定稿）：**排队优先、拒绝为例外**。LLM 中间件拿到 429 要多一轮往返、代价高，所以默认把闸门
  调成「先排队吸收突发、只有队列满或等待超限才 429」。
- 前提：loadtest 需要**真实 SearXNG 上游**与回环访问，且必须在**沙箱外**执行（沙箱内 `aiosqlite` 线程被拦、
  回环不可达、docker socket 被拒）。测试期间入口限流关闭（`UTF8SEARCH_RATE_LIMIT_RPM=0`）以聚焦上游并发；
  各轮背靠背对比，上游引擎状态仍可能漂移，结论按同一时段对比读。

## 2. 12s 的根因（经实测确认）

并发 30 冷查询 + 闸门关，复现了 §4.4 的量级：**P50 10252ms / P95 12505ms**（§4.4：12138 / 12838ms）。
同期日志与指标给出根因证据：**37 次「SearXNG 连接异常，0.4s 后重试一次」+ 30 次上游调用失败（error 30 / ok 32）**。

**根因链**：上游被同时打爆 → 连接异常 / 瞬时错误 → 本地 `_request()` 的**重试一次**再撞在同一批被打爆的上游上
→ 单次尝试上限 5.5s（`search_timeout_limit 2.5 + 3`）× 2 ≈ **11s**。**闸门消掉的就是这一段**：改动后同场景
**重试 0 次、上游 error 0**。

### 3.1 选点标准与结论

标准（用户给定）：

1. **general@10：成功率 ≥ 90% 且 P95 ≤ 6s**，在此前提下取**最小的 `max_wait`**；
2. **general@30：成功率 ≥ 25%、P95 ≤ 6s**，429 全部 < 50ms 返回；
3. **@1：单请求 P50 退化 ≤ 5%**。

逐条对照：

- `queue=6` 在任何 `max_wait` 下 @10 都只有 **18%** → **淘汰**。`queue=12` 才把 @10 拉到 96-100%。
- `queue=12, max_wait=2.5` 满足 @10（96%），但 @30 只有 **18% < 25%** → 淘汰。
- `queue=12, max_wait ∈ {4.0, 6.0}` 同时满足 @10（100%）与 @30（25%，P95 4.98s / 5.38s ≤ 6s）。
  按「取最小的 `max_wait`」→ **选 `queue_limit=12`、`max_wait=4.0`**。
- @1：新默认 vs 基线 P50 813 → 833ms（**+2.5%**，≤5%）✓（见 §4）。

**定稿默认：`MAX_CONCURRENCY=3` / `QUEUE_LIMIT=12` / `MAX_WAIT=4.0`。**

**唯一未达标项（如实记录）**：标准 2 的「429 全部 < 50ms」。@30 下实测 429 时延为
**general 46–329ms（中位 187ms）、news 68–352ms**，未达 50ms。原因不在闸门决策本身——metrics 显示
@30 的拒绝 **reason 全部是 `queue_full`（无 `timeout`）**，即准入时立即决定、没有排队等待；实测时延来自
**单 worker uvicorn + 压测客户端在 30 并发下同时饱和**（事件循环排队 + 客户端侧调度），不是闸门在等。
@10 下 429 时延为 6–116ms（`queue=6` 的 41 条里 40 条 < 50ms），@1 无 429。

- **单请求（@1）无回退**：P50 +2.5%、P95 +2.4%、max +4.6%（阈值 5%）✓；metrics 显示 @1 的
  `acquire_seconds_count=0`，即完全没排队。
- **news@10 双向改善**：P95 7818 → **2236ms**，有效吞吐 1.8 → **7.3 req/s**（成功率保持 100%）。
  news 过去每请求并发占用 2 个槽位；改成**可选补充路非阻塞取容量**后，拿不到容量就跳过（记 `degraded`），

  这正是「排队优先、拒绝为例外」在超出上游容量后的必然结果——若 @10 也达不到 90%，本报告会如实写
  「上游容量上限 ~2 req/s」；实测 queue=12 时 @10 达 100%，故默认档位取 queue=12。

## 6. 指标格式修正（nit）

`render_metrics()` 原先同时输出 `..._rejected_total{reason=...}` 与无标签的 `..._rejected_total <n>`，
Prometheus `sum()` 会重复计数。现**只保留带标签序列**（`requests_total` 本来就是同一风格）；
单测直接断言无标签线不存在。

## 7. 单测（离线，全绿）

`pytest -q -m "not net"` → **254 passed, 4 deselected**（本轮新增：闸门非阻塞 2 条 + 兜底/补充路跳过 2 条等）。

- 闸门：放行 / 排队转交 / 队列满立即拒 / 排队超时拒 / `track()` 记录 / **`try_acquire()` 失败不排队、不写排队直方图、不产生 429 计数** /
  **`track(non_blocking=True)` 抛 `no_capacity`** / Prometheus 文本（含「无标签线不存在」断言）。
- pipeline：过载**不被吞成空结果**；主源过载**不降级兜底源**；**兜底源没容量被跳过（`fallback_no_capacity`）**；
  **news 补充路没容量跳过（`news_general_no_capacity`，且断言用的是非阻塞）**。
- REST/MCP：429 + `Retry-After`；`ToolError` 可读；`/metrics` 渲染与关闭。

## 8. 复现命令

```bash
# 起临时服务（沙箱外；RPM=0 关掉入口限流，聚焦上游并发）
UTF8SEARCH_API_KEYS=lt-key UTF8SEARCH_RATE_LIMIT_RPM=0 UTF8SEARCH_UPSTREAM_MAX_CONCURRENCY=3 \
UTF8SEARCH_UPSTREAM_QUEUE_LIMIT=12 UTF8SEARCH_UPSTREAM_MAX_WAIT=4.0 \
  .venv/bin/python -m utf8_search serve --host 127.0.0.1 --port 8032 &

# 冷查询压测（基线把 UPSTREAM_MAX_CONCURRENCY 设为 0）
.venv/bin/python scripts/loadtest.py --url http://127.0.0.1:8032 --api-key lt-key \
  --concurrency 10 --n 50 --topic general --warmup 2 --json data/final-new-g10.json

curl -sS -H 'X-API-Key: lt-key' http://127.0.0.1:8032/metrics
```

均在 gitignore 的 `data/` 下。

## 9. 已知限制

- 闸门是**单进程**的：`serve` 单 worker 够用；多 worker 需按 worker 数分摊上限（`.env.example` 已写明）。
- @30 的 429 时延（46-352ms）**未达 50ms 目标**，原因是单 worker + 压测客户端同时饱和，不是闸门在等待。
- 高并发下成功率下降是**容量墙**的必然结果（上游 ~2-3 req/s）；要提升只能加上游实例，不能靠调大队列。
