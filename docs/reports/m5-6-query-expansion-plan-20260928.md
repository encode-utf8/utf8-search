# M5-6 查询改写 / 多查询扩展 —— 可行性分析与实施方案（2026-09-28）

> **本轮只做勘察与规划，不写实现、不建开发分支、不动 main。** 本文是待拍板方案。
> 依据：`docs/04` §6（M6 候选：查询改写 / 多查询扩展，价值「提升 recall，接近 Tavily」，成本「中」）
> 与 §4.4（deep 目标「读几十个网页」）、`docs/reports/m5-5.3-*` 的覆盖率/卫生度口径与历史数字。

## 0. 结论摘要（建议）

- **先做「规则式 1 路扩展」，不做小模型改写**：确定性、零依赖、可单测、可随时关；
  小模型改写留到阶段 3，且必须先用量尺证明边际收益。
- **扩展必须与现有闸门同源**（同一 `UpstreamGate`），并且**只做「锦上添花型」**：
  拿不到容量就跳过 + `degraded` 标记，**不 429**（跳过不会导致空结果——这与 news 补充路/Bing 兜底这类
  「兜底型」调用是不同的类别，沿用 M5 的分类判据）。
- **fanout 上限 = 1**（一个用户查询最多额外发 1 路上游，即总 2 路），且**只在「主源不足」时触发**
  （复用 5.2 的不足判据）。理由见 §1/§5：上游容量是硬约束，2 路已经是今天实测的可用上限。
- 预期收益要如实看待：当前客观指标已经不差（覆盖率 0.838、同站冗余/聚合页/脚本不匹配/空内容全 0），
  扩展的主要价值在**长尾与多义查询的候选宽度**（独立站点数、覆盖率、deep 模式可抓页数），
  **不是**「把 2-9 从不可用救回来」。

### 1.3 今日新探：「同一用户并发下，1 路 vs 2 路上游」的真实成本

| 组 | 每用户上游路径 | 成功 | 429 | P50 | P95 | max | 墙钟 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| general（主源 1 路） | ~1 | 30/30 (100%) | 0 | **1715ms** | **3473ms** | 3718ms | 12.8s |
| news（不足时串行补第 2 路） | ~2 | 29/30 (97%) | 1 | **2678ms** | **6290ms** | 7156ms | 18.6s |

**读数**：同一用户并发下多打一路上游 ≈ **P50 +56%、P95 +81%、墙钟 +45%**。

**这条数字就是本方案最重要的约束：扩展把「每用户 1 路」变成「2 路」，等价于把上游压力翻倍。**

### 1.5 需求第 4 条的目标与现状差距

- 需求：像 deepseek 那样一次读几十个网页、效果接近 Tavily。现状 `deep` 已能读约 24 页（`deep_pages=24`），
  但**候选池宽度**受上游单次返回限制（`rank_candidate_pool=24`，SearXNG 一次返回的候选在长尾查询上常常 <24）。
- **差距不在「抓取能力」，在「候选够不够挑」**：候选不足时，质量过滤的「分级补回」会把低质项放回来
  （5.3 §3 的结论），这正是扩展能帮上忙的地方。
  ⚠️ 诚实标注：**「长尾查询实际拿到多少候选（是否常低于 24）」本轮没有测**——阶段 1 的第一件事就是
  把「主源候选数分布」打出来（否则无法判断扩展是否有事可做）。

## 2. 核心矛盾：扩展是**乘法级**放大，必须与闸门同源

1. **闸门是全局的**：`limit=3` 限制的是「同时打到 SearXNG 的聚合请求数」。扩展路如果新开闸门，
   等于绕过保护；因此扩展**必须占用同一个闸门**，并接受「拿不到容量就放弃」。
2. **等价并发被稀释**：fanout=1 时，一个用户请求要占 2 个槽位（主源 + 扩展）→ 同样的 `limit=3`
   只能支撑 **1.5 个用户请求**同时进行；即用户级等效并发从 3 降到 1.5。
   这与 M5 里 news 曾经的困境一模一样（当时 news 每请求并发双打，等效并发 limit/2）。
3. **不得与 news 的兜底叠加**：news 已经是「主源不足 → 串行补一路通用引擎」。如果扩展再来一路，
   单请求最多可能 3 路上游 → 必须**互斥择一**（见 §5 的预算规则）。
4. **缓存是唯一免费的扩展**：扩展查询各自走 `_query_cache_key`，同一扩展词在不同用户查询间可复用；
   长尾查询扩展词重复率低，不能指望它兜底。

## 3. 扩展策略候选与取舍

| 方案 | 例子 | 成本 | 可控性 | 主要失败模式 | 中文长尾 |
| --- | --- | --- | --- | --- | --- |
| **A. 规则式：去/加时间限定词** | 「最近一周 AI 行业动态」→「AI 行业动态」/「AI 行业动态 2026年9月」 | 0 依赖、纯本地 | 高（可单测） | 时间词去掉后候选变旧（与 5.2 时效目标冲突） | 低风险 |
| **B. 规则式：长查询关键词拆分** | 「FastAPI 与 Django 性能对比」→「FastAPI Django benchmark」 | 0 依赖 | 高 | 拆错会引入无关候选；短查询不适用 | 中 |
| **C. 规则式：中英关键词互译（词典式）** | 「新能源汽车 补贴政策」→ 追加「NEV subsidy policy」 | 词表维护 | 中（词表可控） | 词典覆盖不到长尾 → 无效扩展；翻译错 → 偏题 | 高（需保守） |
| **D. 小模型改写** | 用本地 1-3B 模型生成 3 条改写 | 显存/CPU + 权重文件 + 失败重试 | 低（不稳定、不可单测） | 幻觉改写、超时、版本漂移；**显著增加部署复杂度** | 中 |
| E. 上游侧扩展 | SearXNG 的多 category/多引擎 | 低 | 高 | 已在做（5.1/5.3），无新收益 | — |

**建议顺序（已按拍板修订）**：阶段 2 只做 **B（关键词拆分）** → 视数据决定是否加 **A（时间词）**；
**C（中英词典互译）阶段 1/2 都不做**，**D（小模型改写）只在阶段 3 且必须先证明量尺收益**。
理由：B 的触发条件（长查询、多关键词）天然与「候选不足」相关，且**失败模式可控**（拆错最多是多了几条无关候选，
会被 5.3 的覆盖率/同站过滤挡住）；C 对中文长尾有用但需要词表，风险最高；D 的成本/收益在免费服务场景不划算。

## 4. 融合与去重（复用 5.3，防止扩展放大噪声）

**好消息**：融合层已经支持多路 —— `rank/fusion.py::fuse(hit_groups, k=60)` 就是 **RRF（倒数排名融合）**，
天然接受「多组候选」。扩展路只需作为**额外的 hit group** 传进去，不需要新写融合逻辑。

推荐做法（阶段 1 最小改动面）：

1. **扩展路独立成组**：`hit_groups = [主源组, 扩展组]`，RRF 里给扩展组一个**权重上限**
   （例如扩展组每条的基础分 ×0.7，或扩展组最多贡献 `ceil(candidate_pool/3)` 条），避免扩展候选挤掉主源头部。
2. **过滤统一在融合后做**：`apply_rank_filters`（同站限流 / 聚合页 / 脚本一致性 / 覆盖度 / 分级补回）
   对融合后的候选一视同仁 —— 这一步天然抑制「扩展把同站冗余与聚合页放大」。
3. **扩展路内先行一次轻过滤**：扩展组在进入 RRF 前丢掉裸域名标题与明显聚合页（复用 `filter_low_quality`
   与 `is_aggregator_page`），减少无用候选污染 RRF 名次。
4. **URL 去重已在 `fuse` 内**（`normalize_url` 归并），扩展路与主源命中同一 URL 时自动合并、只贡献一次票。
5. **护栏指标**：阶段 1 必须观测「同站冗余 / 聚合页 / 脚本不匹配 / 空内容」四项**不增加**（§6 的必过项）。

## 5. 闸门之下的收敛规则（方案核心）

### 5.1 扩展属于「锦上添花型」，与兜底型分开

| 类别 | 判据 | 拿不到容量时 | 本方案的归属 |
| --- | --- | --- | --- |
| 兜底型 | 跳过会返回空/残缺结果 | **429**（或排队等） | news 通用补充路、Bing 兜底（已有） |
| **锦上添花型** | 少几条候选无妨 | **跳过 + `degraded` 标记** | **查询扩展（本方案）** |

实现上直接用已有的 `UpstreamGate.try_acquire(timeout=upstream_optional_wait)`：
拿到就跑、拿不到就跳过并记 `degraded_reason="expansion_no_capacity"`（与兜底型的 429 区分开）。

### 5.2 预算规则（草案，待拍板）

1. **触发条件**（必须「不足才扩展」）——**阈值由分布选点，阶段 1 不拍数字**：
   - 阶段 1 先测出「主源候选数 / 覆盖率 / 独立站点数」的分布（见 §7 阶段 1），
     再由分布定「候选不足」的具体门槛（例如候选 < 目标值的某个比例、或覆盖率 < 某值）；
   - 在没有实测分布之前，**只用 5.2 的原始判据占位**：候选数 < 目标候选池（`rank_candidate_pool`）即视为不足。
   反之（候选充足）**不扩展**，省下容量给其它请求。
2. **fanout 上限**：1 条扩展（总 2 路）。阶段 3 之前不放开到 2。
3. **互斥规则**：`news` 主题下若已触发兜底型补充路（串行第二路），**不再扩展**；
   二者共享「本请求第 2 路」的预算。
4. **等待预算**：扩展路用 `try_acquire(timeout=upstream_optional_wait)`（默认 1.0s）——**不进主源队列**，
   不占用主源的排队额度；等不到就放弃。
5. **缓存策略**：
   - 扩展查询各自走查询级缓存（`hits:<fingerprint>`），跨请求复用；
   - 主源结果缓存（`res:` 最终包）不受影响；
   - 扩展若被跳过，**不写**「带扩展」的缓存，避免把降级结果固化。
6. **可观测**：`/metrics` 增 `expansion_attempted_total` / `expansion_skipped_total{reason}` /
   `expansion_upstream_seconds`（阶段 1 一并做，便于判断是否值得留）。

## 6. 量尺与验收设计

### 6.1 主指标（必须）

用 `scripts/relevance.py`（20 条中英查询，四类各 5 条）+ 5.3 的客观卫生度：

```bash
# 采集（联网，约 1-2 分钟）
.venv/bin/python scripts/relevance.py --depth basic \
  --hygiene-out data/expansion/hygiene-after.json --out data/expansion/relevance-after.md
# 人工打分（唯一需要判断的一步）
.venv/bin/python scripts/relevance.py --score-file data/expansion/relevance-scores.csv
```

对照基线（2026-09-28 实测）：`100 条结果 / 覆盖率 0.838 / 同站冗余 0 / 聚合页 0 / 脚本不匹配 0 / 空内容 0 / 独立站点 4.7`。

### 6.2 判定标准（建议）

**必过（任一不满足即判失败）**

| 维度 | 门槛 |
| --- | --- |
| 覆盖率均值 | ≥ 基线 ×0.95（不得实质下降） |
| **新增独立站点数** | **> 0（硬指标）**：扩展候选必须给最终结果带来**新域名**；**无新增即判失败**（说明扩展只是在重复主源） |
| 同站冗余 / 聚合页 / 脚本不匹配 / 空内容 | **不增加**（与 5.3 的 `evaluate_hygiene_delta` 一致） |
| 独立站点均值 | ≥ 基线（不得下降） |
| 延迟（@5、n=30、basic） | P95 ≤ 基线 ×1.5 且 **≤6.5s** |
| 成功率（@5） | ≥95%，且 **429 = 0** |
| 上游健康 | `/metrics` 的 `upstream_requests_total{result="error"}` **= 0** |
| 降级/跳过可见 | `expansion_skipped_total{reason}`（或结构化日志）**必须有计数**，不允许静默跳过 |

**期望（用于判断是否值得加码）**

- 覆盖率均值 +0.03 以上，或独立站点均值 +0.3 以上（二选一）；
- 2-9 人工打分（top5 相关数 ≥4 的查询占比）不低于当前基线（当前基线待人工填，见
  `docs/reports/manual-acceptance-checklist-20260928.md`）。

**判失败后怎么办**：先关扩展（配置开关，默认关）回到基线；只在「扩展命中率低但覆盖率有提升」时
才考虑换规则（A/C）或提高门槛，**不做「调大闸门换扩展」**——那会把坏日的保护一起丢掉。

### 6.3 受控 A/B（推荐做法，避免上游漂移）

免费源同一查询隔几秒 top1 都可能变。沿用 5.3 的方法：先用 `scripts/rank_ab.py` 的候选快照思路，
把「主源候选 + 扩展候选」落盘，再对**同一批候选**分别按「含扩展组 / 不含扩展组」排序，隔离排序侧差异；
端到端对比则**背靠背交替**跑两轮（扩展开/关）取区间。

## 8. 风险清单与缓解

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| **上游被放大**（首要） | 扩展把 1 路变 2 路，坏日直接压垮上游 | 同源闸门 + 非阻塞取容量 + 「不足才扩展」+ fanout=1 + 默认关；`upstream error` 一旦 >0 立即回退 |
| 延迟上升 | 今日实测 2 路 ≈ P95 +81%（同用户并发 @5） | 扩展与主源**并行**发出（不是串行）、但受闸门；P95 预算 1.5×，超了就关 |
| 免费源反爬 | 请求数上升会加速引擎被限流/封 | 用 5.1 的引擎健康度：`engines.cooling` 非空时不做扩展 |
| 中文长尾退化 | 词典式翻译对长尾无效，拆词可能引入无关候选 | 只在「不足」时扩展；覆盖率守卫 + 同站/聚合页过滤不动；C 规则最后做 |
| 缓存命中率下降 | 扩展查询是新 key，单请求缓存条目增多 | 扩展查询按查询级缓存；跳过时不写缓存；观测命中率 |
| 结果同质化 | 扩展候选与主源高度重合（浪费容量） | RRF 内 URL 去重天然合并；阶段 1 统计「扩展贡献的新域名数」，为 0 则说明规则无效 |

## 9. 拍板结论与剩余待定

**已拍板（2026-09-28，见 §0.1）**：

1. **fanout 上限 = 1**（总 2 路）；
2. **触发阈值由分布选点** —— 阶段 1 只测分布，不先拍数字；

   降级/跳过**必须进计数**；阶段 2 验收需产出**可直接打分的明细表**；
5. 阶段拆分：**阶段 1 = 埋点测量（零额外上游调用）**，**阶段 2 = 规则扩展实现（默认关的开关）**。
