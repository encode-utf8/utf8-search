## 4. 阻塞点：阿里云安全组（需用户手工处理）

### 4.1 证据

Caddy 申请证书时，Let's Encrypt 两种校验方式都失败：

```
challenge_type=tls-alpn-01 failed:
  "43.106.104.49: Timeout during connect (likely firewall problem)"
challenge_type=http-01 failed:
  "Fetching http://43.106.104.49.sslip.io/.well-known/acme-challenge/...:
   Timeout during connect (likely firewall problem)"
```

独立第三方从公网探测（`r.jina.ai` 中转），80 与 443 均 `TimeoutError`。

### 4.2 排除本机原因

| 检查 | 结果 |
| --- | --- |
| `ufw status` | `inactive` |
| `iptables -S INPUT` | `-P INPUT ACCEPT`，无 DROP 规则 |
| Docker NAT 规则 | 80/443/443udp 的 DNAT 均存在 |
| 本机监听 | `0.0.0.0:80`、`0.0.0.0:443` 正常 |

→ 本机全放行，超时只能来自**云安全组入方向**。

### 4.3 需要的动作

在阿里云控制台把安全组入方向改为只放行 **22 / 80 / 443**，然后：

```bash
# 必须先删掉缓存的自签证书：只 restart 的话 Caddy 会复用存储里那张未过期的证书、不会重新申请
docker compose exec -T caddy sh -c "rm -rf /data/caddy/certificates/local/43.106.104.49.sslip.io"
docker compose restart caddy
docker compose logs caddy --since 2m | grep -i "certificate obtained"
```

该流程已预演验证：删除自签证书 + 重启后，Caddy 确实重新走了一遍 ACME（`http-01` 与 `tls-alpn-01` 均因
`Timeout during connect` 失败），随后回退自签，服务全程 200 不中断；安全组放行后同样操作即可拿到真证书。

**不要把 8000/8888 加进安全组**：它们只绑回环，加了也没用。

## 5. 本轮修掉的问题

### 5.1 Caddy 吞掉不匹配 Host 的请求，导致 421 防护失效（已修）

现象：经 Caddy 发 `Host: rebind.example` 得到 **200 空响应**（`server: Caddy`），而不是应用应返回的 421。

原因：两处

1. Caddy 默认会把 Host 改写成站点/上游地址，应用看不到真实 Host；
2. Host 不匹配任何站点时，Caddy 自己返回空 200，请求**根本没转发给应用**。

修复（`Caddyfile`）：

```caddyfile
reverse_proxy utf8-search:8000 {
    header_up Host {http.request.host}   # 透传客户端原始 Host
}

# 兜底站点：任何 Host 都交给应用判定（应用才是白名单唯一的判定点）
:443 {
    tls internal
    reverse_proxy utf8-search:8000 { header_up Host {http.request.host} }
}
```

修复后：伪造 Host → 421（`server: uvicorn`）。

### 5.2 新增应用容器健康检查（已加）

应用服务原来没有 healthcheck，`docker compose ps` 只显示 `Up`。已补（镜像无 curl，用自带 python 探 `/health`），现在显示 `Up (healthy)`。

## 6. 阶段 A3 收尾：自检脚本自身缺陷（均已修复）

### 6.1 时效性判定与产品口径不一致（窗口 3 天 vs 7 天、最差值 vs 比例）

- 位置：`scripts/mcp_selfcheck.py`（REST 通道「days=1 → time_range=day」一项）。
- 旧实现：`worst = max(ages)` 后判 `worst <= 3.0` —— **既把窗口卡死在 3 天，又拿「最旧一条」当判据**。
- 与产品口径的出入：
  - M5-5.2 报告与 `docs/04` 第 5.2 节的达标标准是「**带 7 日内发布日期**算达标，**门槛 ≥ 80%**（比例）」；
  - `.env.example` 的 `UTF8SEARCH_NEWS_FRESH_DAYS=7` 同样是 7 天。
  - 结果：只要混进一条 5 天前的聚合帖，这项就被打红 —— 2026-09-25 的 23/24 正是此因，
    **这是自检脚本引入的判定缺陷，不代表产品新鲜度变差**。
- 修法：
  - 窗口：`3.0` → `min(settings.news_fresh_days, 7)`（部署可以更严，但不能放宽到 7 天以上）；
  - 判据：**最旧一条 ≤ 阈值** → **带日期结果中落在窗口内的比例 ≥ 80%**；
  - 结论文案同时给出比例、窗口、最旧多少天（最旧值只作诊断，不参与判定）；
  - 抽成纯函数 `evaluate_news_freshness()` / `news_fresh_window_days()`，回归用例见 `tests/test_mcp_selfcheck.py`。
- 影响：本轮主命令一次跑出 **24/24、exit 0**。

### 6.2 `--api-key` 与 ratelimit 通道实例 Key 不一致

- 位置：`scripts/mcp_selfcheck.py`（ratelimit 通道起独立实例处）。
- 旧行为：`LocalServer(rate_limit_rpm=1, ...)` 用默认 Key `selfcheck-key`，
  而 `check_ratelimit(..., api_key=args.api_key)` 传的是**命令行给的 Key**，两者不一致。
- 影响：只要用 `--api-key` 指定自定义 Key（本轮验收就是这么跑的），ratelimit 两项必然 401。
- 修法（一行）：

  ```python
  server = LocalServer(api_keys=args.api_key, rate_limit_rpm=1, note="限流自检实例")
  ```

### 6.3 自检报告会把 API Key 原样写进报告

- 位置：`scripts/mcp_selfcheck.py`（报告「服务实例」一行）。
- 旧行为：把完整 `--api-key` 原样打印进报告，归档/分享即泄露。
- 修法：新增 `mask_api_key()`（前 4 位…后 4 位，短板整体打码），所有服务实例文案只输出掩码；
  `render_report` 再兜底把明文替换成掩码。A3 复核确认本轮报告**不含完整 Key**。

## 7. 附加观测：`google news` 引擎

### 7.1 本轮数据

| 阶段 | 观测 |
| --- | --- |
| 部署后第一批 6 条 news 查询 | **6/6 失败**，`failed_engines=['google news']` |
| `/health` 快照 | `google news`：`class=captcha`、`reason=暂停服务: 验证码`、`consecutive_failures=6`、`retry_after≈3581s`；同批 `google`(通用) 也是 `captcha` |
| SearXNG 直连隔离测 | `unresponsive_engines=[['google news','Suspended: CAPTCHA']]`，结果 0 条 |
| **重启 SearXNG 清空处罚盒后** | `google news` **6/6 成功**（每次 10 条，`unresponsive=[]`） |
| 同期 `google`(通用) 隔离测 | 4/4 成功（9–10 条） |
| 本机直连 `https://www.google.com/search?q=test` | 200，真实结果页（`<title>Google Search</title>`，无 CAPTCHA/consent 关键词） |

### 7.2 结论

**不是"这台机器的 IP 被 Google 永久风控"。** 证据链：

- 同一台机器、同一个 IP，重启 SearXNG 后 `google news` 立刻 6/6 成功；
- 本机直连 Google 搜索页稳定 200，无风控页面；
- 失败集中在"连续查一批 news"这段时间，且 SearXNG 报的是 `Suspended: CAPTCHA`——这是 SearXNG **自己的处罚盒**：
  引擎被判定一次后，SearXNG 会在一段时间内**直接返回 Suspended、不再真正发起上游请求**，所以表面上会连续多轮"100% 失败"。

即：Google 对 SearXNG 的请求指纹（无 Cookie、固定 UA、机房 IP 段）会**间歇性**触发验证码；
一旦触发，SearXNG 会自锁一段时间。本服务的引擎健康度自适应会按失败原因给 30 分钟冷却并自动恢复（`consecutive_failures` 指数退避、封顶 3600s），行为符合 M5-5.1 设计。

### 7.3 换源建议（不改代码，只调配置）

如后续希望降低对 Google 的依赖：

3. 排障时若要区分「SearXNG 处罚盒」与「真的不可达」，先 `docker compose restart searxng` 再隔离测一次（手册 §8.1）。

## 9. 收尾说明（供后人读历史时对齐口径）

### 9.1 时效性阈值判定曾与产品口径不一致 —— 属自检脚本缺陷

自检脚本 REST 通道「days=1 → time_range=day」一项，**原判据是「最旧一条 ≤ 3 天」**，
与 M5-5.2 报告、`docs/04` 第 5.2 节、`.env.example` 的 `UTF8SEARCH_NEWS_FRESH_DAYS=7` 均不一致：

- 窗口：3 天 vs 产品 7 天；
- 判据：最差值 vs 产品「比例 ≥ 80%」。

因此 2026-09-25 那次 23/24，是**自检脚本自身的判定缺陷**，**不代表产品新闻新鲜度变差**。
本次（阶段 A3）已把窗口对齐为 `min(settings.news_fresh_days, 7)`、判据改为
「带日期结果中落在窗口内的比例 ≥ 80%」，最旧天数仅作诊断输出。
后人读到这段历史时，请勿误判为产品新鲜度回归。
