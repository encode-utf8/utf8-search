# M6 阶段 1：查询扩展埋点测量报告（2026-09-28）

- 分支：`feature/m6-query-expansion-measure`（基于 `main` @ `8646dc9`）
- 目标（用户 2026-09-28 拍板）：**零额外上游调用**地测量「主源候选数 / 目标候选池 / 查询词覆盖率
  （分母=用户原始查询词）/ 独立站点数 / 是否命中候选不足判据」的分布，**由分布选点**，并判断阶段 2 是否值得做。
- 方案与拍板结论：`docs/reports/m5-6-query-expansion-plan-20260928.md`

## 0. 结论（先说要点）

1. **「候选不足」判据几乎不触发：占位口径（候选数 < 目标候选池）触发率 = 2.9%（1/35）**。
   主源在 34/35 条查询上都给满了目标候选池（24 条），**「候选不够」这个前提基本不成立**。
2. 按**覆盖率**作为信号才有区分度，但仍偏低：覆盖率 < 0.6 → **8.6%**；< 0.5 → 5.7%；
   只有把门槛放到 < 0.8 才会到 45.7%（那等于「对一半查询都扩展」，成本翻倍，不建议）。
3. **独立站点数已经接近天花板**：均值 4.63/5，23/35 条查询的 top5 **全部来自不同域名**。
   因此「**扩展组新增独立站点数 > 0**」这条硬指标**头部空间很小**（最多再挤进 ~0.4 个名额），
   很容易出现「无新增」的失败判定。
4. **阶段 2 的收益上限有限**（如实记录）：触发面约 9%（覆盖率口径），可提升的头部空间 <1 个名额/查询。
   若仍要做，建议**以覆盖率 <0.6 为触发条件**、**默认关的开关**，并把目标明确限定为**中文长尾**
   （数据支持：长尾组覆盖率均值 0.726 < 抽检组 0.838，覆盖率最低的 3 条里 2 条是长尾）。

## 1. 方法（怎么保证「零额外上游调用」）

- 每条查询只走**现有那一次**主源调用：脚本直接复用 `SearchPipeline._collect_hits()` + `_rank_hits()`
  （与 `scripts/rank_ab.py` 同一套内部接口），**不发起任何新的上游请求**；覆盖率/站点数在本地对
  已拿到的候选计算。
- 判定逻辑抽成纯函数 `utf8_search.verify.expansion.expansion_needed(candidates, target, coverage_mean, *,
  min_coverage=None)` —— 阈值全部由调用方给，**代码里不写死数字**（按「由分布选点」的要求）。
- 覆盖率分母固定为**用户原始查询词**（`rank.diversity.query_coverage(request.query, item)`），
  扩展/改写词不参与计算。
- 采样配置：`depth=basic`、`max_results=5`、**单并发顺序执行**；查询集 = 2-9 的 20 条抽检查询
  + 15 条中文长尾查询（地方政策 / 品类商品 / 标准规范类）。

```bash
.venv/bin/python scripts/expansion_measure.py --out data/measure/expansion-samples-20260928.json
```

## 3. 阈值扫描与选点建议（回算，不额外发请求）

| 触发条件 | 预计触发率 |
| --- | --- |
| 候选数 < 24（= 占位判据，5.2 原始口径） | **2.9%** |
| 候选数 < 16 / 12 / 8 / 6 | 2.9% / 0% / 0% / 0% |
| 覆盖率 < 0.4 | 2.9% |
| 覆盖率 < 0.5 | 5.7% |
| **覆盖率 < 0.6** | **8.6%** |
| 覆盖率 < 0.8 | 45.7%（≈ 对一半查询扩展） |
| 候选 < 24 **或** 覆盖率 < 0.6 | 8.6% |

**建议（阶段 2 若做）**：触发条件取 **「覆盖率 < 0.6」**（或更保守的 0.5），
**候选不足作为次要条件保留**（它单独只有 2.9%，但成本几乎为零）。
**不建议**取覆盖率 < 0.8：触发率跳到 45.7%，等于把所有请求的上游成本翻倍，与闸门保护直接冲突。

## 4. 阶段 2 是否值得做（结论）

**收益上限有限，建议做成「默认关的实验开关」，并把验收目标限定为中文长尾。** 依据：

1. 触发面小：按覆盖率 <0.6 只有 **8.6%** 的查询会扩展 —— 对整体指标的拉动上限就是这条边界的改善；
2. 头部空间小：独立站点数已 4.63/5，硬指标「新增独立站点数 > 0」最多再挤进 ~0.4 个名额/查询，
   **很可能直接判失败**（这正是必须把它设为硬指标的意义）；
3. 唯一的明确机会点是**中文长尾**（覆盖率 0.726 vs 0.838，最低的几条都在长尾组）——
   若做，就明确「为长尾查询换 1 条更贴题的候选」，而不是宣称整体 recall 大幅提升。

**若阶段 2 判失败的预期形态**（提前写清，避免事后找补）：触发查询数只有 3/35，若其中改善 ≤1 条，
覆盖率均值变化会落在噪声内（<0.01），「新增独立站点数」也很可能为 0 → 按方案 §6.2 判失败并停用开关。

## 5. 局限与注意

1. **单次采样**：上游漂移会让候选/覆盖率上下浮动；建议阶段 2 前后各跑 3 次取中位数（本轮为控制上游压力只跑 1 次）。
2. **候选数被目标候选池压平**：34/35 条正好等于 `rank_candidate_pool=24`，说明「候选不足」在这种参数下
   天花板很低。若把候选池调大（32/48）再测，触发率可能上升 —— 但那可能只是「要得更多」，
   需要一个独立实验确认，**本轮不下结论**。
3. 覆盖率是**词面匹配**指标，长中文查询天然偏低（含「案例 / 流程 / 条件」这类非检索词），
   因此它更适合当**相对信号**（哪条查询更需要扩展），而不是绝对质量分。
4. 本轮只测了 `basic` + `max_results=5`；`advanced/deep` 的候选池目标不同（含页数预算），分布需另测。
