## 1. 取证

### 1.1 快照口径（`scripts/ops_check.py`，cron 每 5 分钟）

列：`ts, health_status, upstream_error, rejected_queue_full, rejected_timeout, requests_ok, probe_results`
（`rejected_*` 与 `requests_ok` 是**自容器启动以来的累计值**；`probe_results` 是单条探针查询返回的条数）。

### 1.2 「坏日」口径（三层，先定义再统计）

| 层 | 判据 | 说明 |
| --- | --- | --- |
| **L1 压力事件** | 任一采样 `upstream_error>0` 或 `rejected_queue_full>0` 或 `rejected_timeout>0` | 最直接：闸门真的拒绝过 / 上游真的报过错 |
| **L2 上游劣化** | `probe_results` 连续 ≥2 次 <5（或窗口中位显著低于好日基线 5） | 探针拿不满结果 ≈ 上游部分引擎失效 |
| **L3 端到端尾延迟** | 单请求 **P95 ≥ 8s**（"19s 级"即 docs/04 §4.4 记录的坏日） | **当前快照没有延迟列** → 需要下一轮补采（见 §3.1） |

### 1.3 统计结果

| 指标 | 值 |
| --- | --- |
| 样本行数 / 跨度 | 322 行 / 47.9h（按 5 分钟应有 576 行 → **覆盖率 56%**；2 个 >6min 缺口，最大 **22h**） |
| `upstream_error` | max **0**，>0 行数 **0** |
| `rejected_queue_full` | max **0**，>0 行数 **0** |
| `rejected_timeout` | max **0**，>0 行数 **0** |
| `probe_results` | min/中位/均值 = **5 / 5 / 5.00**，==5 占比 **100%**，<5 行数 **0** |
| `health_status` 非 200 | 1 行（09-30 09:40 首次写入的空值行） |
| 放行 / 闸门拒绝增量 | **877 / 0 + 0** → 放行占比 **100%**（跨 5 次容器重启的计数器重置已跳过分段） |

**旁证**：最终镜像与旧镜像的 6h/24h 长稳 P95 为 **2.1-2.6s、max ≤2.6s**（无 19s 级事件）；
项目里出现过的"坏日"全部来自 **受控压测的人造高并发**（M5 §7.1 news@30：baseline P95 6.5-9.6s vs 闸门 4.9-6.6s；
docs/04 §4.4 记录的 19s 级也是压测场景），**没有一次自然观测**。

## 2. 判定：样本不够（依据）

1. **L1/L2 命中为 0**：47.9h 里闸门从未拒绝、上游从未报错、探针从未掉结果；
2. **观测面不匹配**：日常负载只有 ops 探针（每 5 分钟 1 次）+ 低频外部请求，**根本压不到 limit=3**，
   所以"坏日"若要出现，必须依赖外部流量自然上来（当前没有）或受控压测（人造，不算）；
3. **数据质量不足**：覆盖率 56%（两个大缺口）、无延迟列、5 次容器重启打断计数器连续性 ——
   即使出现坏日，也难把"是上游劣化"与"是重启/缺口"分开；
4. **算法风险**：自适应要在"健康日放宽（拿吞吐）/ 坏日收紧（保上游）"之间切换，**误判方向会放大故障**
   （坏日放宽 → 把上游彻底打爆；健康日收紧 → 无故多付 429）。没有 ≥3 个独立坏日样本，无法验证滞回与上下限。

## 3. 继续采集方案（下一轮实施；本轮不动代码）

### 3.1 快照增列（`scripts/ops_check.py`，下一轮）

| 新列 | 目的 |
| --- | --- |
| `probe_latency_ms` | 探针端到端延迟（补上 L3 判据的数据源） |
| `rejected_queue_full_delta` / `rejected_timeout_delta` / `requests_ok_delta` | 窗口化增量（替代跨重启失真的累计值） |
| `gate_active` / `gate_waiting` | 闸门当前占用与排队（gauge） |
| `cooling_engines` | 冷却引擎数（上游健康度最灵敏的侧写） |

### 3.2 触发条件（定义"样本够了"）

**累计满足以下任一条即可立项实施**：

* **A**：≥**3 个独立坏日时段**（每段 ≥30min）满足 L1，或 L3（探针 P95 >8s）且伴随 `probe_results<5`；
* **B**：≥**5 次尾延迟尖峰**（相邻两次采样内探针延迟升高 ≥3× 好日 P50）且闸门拒绝率 >0 的样本 ≥20 个；
* 采集期要求：快照覆盖率 ≥90%、无 >1h 缺口、单容器连续运行 ≥72h。

## 4. 候选自适应算法设计要点（实现放在立项后）

* **信号**（滚动 5-15 分钟窗口）：上游错误率、闸门拒绝率、探针 P95/P50 比值、冷却引擎数；
* **动作方向**：
  * 坏日（错误率↑ 或 P95↑）：`limit 3→2`、`queue 12→6`、`max_wait 4.0→2.5`（更快 429，先保上游）；
  * 健康日：`limit 3→4`（**上限 4-5，不回到历史 6**），`queue` 不动；
* **稳定机制**：滞回（进入/退出阈值分开）、最短驻留 ≥10min、单步只允许 ±1、上下限硬钳制；
* **开关与回滚**：`UTF8SEARCH_UPSTREAM_ADAPTIVE=1` 才启用（**默认关 = 完全等于冻结值 3/12/4.0/1.0**），
  关闭即一键回滚；不做多 worker（闸门是进程内计数）；
* **风险**：振荡；坏日收紧引发客户端重试风暴；健康日放宽把上游推入惩罚；指标噪声（探针密度不足）；
* **验收判据（实施轮）**：受控压测"人造坏日"下 **成功率不降、P95 不升 >10%、429 数量不增**，
  且健康日基线不得退化（@1/@10 与冻结值同档）；全部原始数据留档。
